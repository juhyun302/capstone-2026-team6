# 평가 데이터 — 골든 케이스와 eval 세트

> 상태: 초안(2026-11-03 갱신, 2026-11-12 키를 강의 7 지침의 `graders`로 바꾸고 범위 밖·추출 인젝션·판정지 후보 검토 케이스를 더함). 데이터 구성과 라벨링 절차를 정하고 해설 초안을 준비하는 단계다. 현재 AI 해설 초안 7건·사람이 AI를 활용해 쓴 해설 3건이며, 모두 사람 검산 전이다. 지표·채점기·러너·베이스라인은 강의 7 evals 설계에서 정한다.

## 1. 두 종류의 데이터

| | 골든 케이스 | eval 세트 |
|---|---|---|
| 대상 | 모델 호출 없이 결과가 정해지는 코드 | 모델 출력이 들어가는 판정 |
| 판정 | 케이스별 통과·실패. 1건이라도 실패하면 불합격 | 지표와 임계값 |
| 위치 | `tests/harness/*.yaml` | `evals/evalset.jsonl` |
| 예 | `validate_solution_idea`, 재포장 검출, 표기 검사, `approval_status` 고정 | 두 요소 추출(AC1·AC8), 결함 탐지(AC3·AC4·AC5), 거부 동작(AC2·AC9) |

같은 원문·후보를 두 곳에서 함께 쓸 수 있다. 결정적으로 판정할 수 있는 항목은 골든 케이스로 옮기고, 나머지만 eval 세트에 둔다.

## 2. 파일

- `evalset.jsonl` — eval 케이스. 한 줄에 한 건.
- `source_pool.md` — 원문 후보 목록, 용도, dev 구분.
- `prompts/explanation_draft.md` — AI 해설 초안 프롬프트, 사용 절차, 해설 파일 양식.
- `explanations/README.md` — 해설 초안 색인, 날짜별 작성 방식과 정답 대조 기록.
- `explanations/<원문 ID>.md` — 해설 초안과 사람 검산 기록. `검산 완료`로 확정한 판만 두 라벨러의 공통 입력으로 쓴다.
- `labeling/extraction_form.md` — 두 요소·메커니즘 라벨 양식.
- `labeling/review_form.md` — 후보 결함 라벨 양식.
- `labeling/drafts/<케이스 id>.<라벨러>.md` — 라벨러별 독립 초안.
- `labeling/final/<케이스 id>.md` — 합의 결과. `evalset.jsonl`의 `expect`는 이 파일에서 옮긴다.

## 3. `evalset.jsonl` 키

강의 7 지침의 키(`id`, `category`, `query`, `expect`, `graders`, `note`)에 `split`과 `status`를 더한다.

| 키 | 값 |
|---|---|
| `id` | 접두어 + 원문 ID. `ext-` 추출, `hal-` 요소 부족, `fmt-` 입력 형식, `clr-` 판독 불가, `cnf-` 입력 충돌, `rev-` 후보 검토, `inj-` 지시문 삽입, `oos-` 입력 범위 밖 |
| `category` | 4절 범주 |
| `query` | `tool`(`generate_linked_question`/`review_candidate`), `source`(원문 ID), `input_format`(`text`/`image`/`mixed`), `curriculum_scope`. 필요하면 `candidate`(후보 위치), `variant`(원문을 바꾼 방법), `input`(팀이 직접 쓴 입력 본문. 평가원 원문은 넣지 않는다) |
| `expect` | 온톨로지 필드로 쓴 기대값. 라벨 확정 전에는 `null`이거나 의도한 값 |
| `graders` | 적용할 채점기 목록. `code`(상태·필드 대조), `judge`(LLM-as-judge. 두 요소·메커니즘의 의미 비교, 검토 이유의 품질). 정하는 규칙은 [EVAL_DESIGN 2절](EVAL_DESIGN.md#2-데이터셋-구성) |
| `split` | `dev` / `holdout` / `unassigned` |
| `status` | `PLANNED`(만들 예정) → `UNLABELED`(입력 준비됨) → `LABELED`(사람이 확인함. 2인 합의가 원칙이고, v1 측정은 1인 확인도 허용하며 `note`에 라벨러 수를 적는다). `SEED`는 이전 1인 판정을 옮긴 것으로 다시 라벨링해야 한다 |
| `note` | AC 번호, 라벨 근거, 라벨러와 날짜 |

- `expect.verdict_not`은 허용하지 않는 `verdict` 값 목록이다.
- AI가 낸 결과는 모두 `approval_status=PROVISIONAL`이어야 한다(AC7).
- `LABELED`가 아닌 케이스는 점수에 넣지 않는다.
- `graders`에 `judge`가 있는 케이스의 judge 판정은 사람 라벨과의 일치율 80% 이상을 확인하기 전까지 사람이 채점한다.

## 4. 범주

| 범주 | Aleph 상황 | AC |
|---|---|---|
| `extraction` | 원문·해설에서 두 요소와 메커니즘 추출 | AC1, AC8 |
| `hallucination` | 해설에 요소가 하나뿐인데 두 번째 요소를 지어냄 | AC2 |
| `clarify` | 판독할 수 없는 이미지 | AC9 |
| `conflict` | 이미지와 텍스트의 수식이 다름 | AC9 |
| `constraint` | 결함·교육과정 이탈·수치만 바꾼 후보를 `USE`로 표시하지 않음. 정상 대조군 포함 | AC3, AC4, AC5, AC7 |
| `injection` | 원문·해설·후보 안의 지시문이 추출이나 판정을 바꿈 | AC1, AC4, AC7 |
| `out_of_scope` | 비수학 문항처럼 입력 범위 밖 | AC2, SPEC 4절 비포함 |

`out_of_scope`의 기대 동작은 SPEC에 없어 [EVAL_DESIGN 1.1](EVAL_DESIGN.md#11-v1-측정-지표--풀이-아이디어-추출-단계)의 M8(`QUESTION_ERROR`)을 따른다(2026-11-12 추가).

## 5. 원문 출처

- 평가원 6월·9월 모의평가와 수능 문항만 쓴다. 원문 ID는 `2027-06-common-11`처럼 `학년도-월-영역-번호`로 쓴다.
- 학원·출판사 교재와 사설 모의고사의 원문, 그 원문을 옮긴 해설, 외부 검수 의견은 넣지 않는다. 이 저장소는 공개 저장소다.
- 평가원은 해설을 내지 않는다. 해설은 팀이 쓰거나 AI 초안을 사람이 검산해 쓴다([초안 프롬프트](prompts/explanation_draft.md)). 다른 기관의 해설을 옮기지 않는다.
- AI 초안은 Aleph 추출에 쓰는 모델과 다른 모델로 쓴다. 같은 모델이 쓴 해설에서 추출하면 점수가 실제 사용 환경보다 좋게 나올 수 있다. 작성 주체와 모델명은 해설 파일의 `explanation_origin`과 `작성 모델·버전`에 남기고, 점수는 해설 출처별로도 나눠 본다.
- `explanation_origin`은 `AI 초안`(프롬프트로 생성), `사람 작성`(AI 없이 작성), `사람 작성(AI 활용)`(사람이 생성 도구와 AI를 써서 작성) 중 하나다. 마지막 값은 본문에 모델 출력이 들어갈 수 있어 `사람 작성`과 따로 집계한다.
- 실제 사용 환경을 반영하기 위해 원문 10문항 중 2~3문항의 해설을 사람이 쓴다. 2026-11-02에 AI 초안 7건을 만들고, 2026-11-03에 공통 10·11번·미적분 29번을 사람이 해설생성기와 AI를 활용해 썼다. 현재 구성은 AI 초안 7건·사람 작성(AI 활용) 3건이다. [날짜별 작성 기록](explanations/README.md)에 작성 방식과 사람 검산 전 상태를 구분한다.
- 원문 텍스트·이미지의 저장 방식은 평가원 이용 조건을 확인한 뒤 정한다(9절). 그전까지 `evalset.jsonl`은 원문 ID만 가진다.

## 6. 라벨링 절차

1. 두 라벨러가 서로의 초안과 모델 출력을 보지 않고 양식을 따로 작성한다.
2. 두 초안을 비교해 합의하고 `labeling/final/`에 남긴다. 합의하지 못한 문항은 이유를 적고 강사 확인을 요청하거나 제외한다.
3. 결함을 주입한 후보는 라벨러가 직접 풀어 결함이 실제로 생겼는지 확인한다. 확인하지 못하면 `LABELED`로 올리지 않는다.
4. 합의 결과를 `expect`로 옮기고 `status=LABELED`로 바꾼 뒤 `note`에 라벨러와 날짜를 적는다.
5. 확정한 라벨은 모델 결과를 보고 바꾸지 않는다. 바꿔야 하면 이유와 날짜를 `labeling/final/` 파일에 남긴다.

## 7. dev와 holdout

- 스파이크와 프롬프트 작성에 쓴 원문은 `dev`다.
- 새 원문은 라벨을 확정한 뒤 첫 모델 실행 전에 약 30%를 추첨해 `holdout`으로 둔다. 추첨 방법과 시드를 이 문서에 기록한다.
- 개발 중에는 holdout 결과를 보지 않는다. 개선 후 측정은 holdout으로 한다([PROBLEM.md 5절](../docs/PROBLEM.md#5-성공의-정의)).

## 8. 첫 묶음 목표

| 묶음 | 수량 | 구성 |
|---|---|---|
| 추출 | 15건 | 원문 10건 + 형식·판독·충돌·요소 부족 파생 5건 |
| 후보 검토 | 30건 | 정상 대조군 10, 타당성 결함 8, 교육과정 이탈 6, 수치만 변경·메커니즘 소실 6 |

현재 `evalset.jsonl`에는 42건이 있다. 신규 원문 10건, 파생 5건, dev 추출 3건, 스파이크 판정 SEED 3건, 결함 유형별 예정 7건, 지시문 삽입 2건(검토·추출), 범위 밖 2건, 판정지 후보 검토 10건(외부 전문가 1인 판정)이다. 범주별 수와 채점 규칙은 [EVAL_DESIGN 2절](EVAL_DESIGN.md#2-데이터셋-구성)에 있다.

신규 원문 10건의 해설은 준비했으며, 2026-11-02의 AI 초안 7건은 번호 붙인 단계 형식, 2026-11-03에 사람이 AI를 활용해 쓴 3건은 해설생성기 본문 형식이다. AI 보조 정답 대조는 10건 모두 일치했지만 사람 검산과 라벨 합의는 아직 하지 않았다. 후속 3건은 HWPX·PDF·PNG 변환과 출력 확인을 마쳤으며, 변환 출력본은 저장소 밖에 둔다. 해설 초안 추가로 `evalset.jsonl`의 기대값·상태·split이나 라벨을 변경하지 않았다.

## 9. 미정 사항

- 평가원 원문 텍스트·이미지를 저장소에 둘지, 둔다면 출처 표기 방식.
- AC9에서 "확인이 필요한 부분"을 반환하는 형식과 상태 값. SPEC 5절에 정해지지 않았다.
- 입력 범위 밖 요청(비수학 문항 등)의 기대 동작. v1 evals는 EVAL_DESIGN 1.1 M8을 따른다.
- `judge` 채점기의 프롬프트(`evals/judge_prompt.md`)와 일치율 검증 절차(강의 7, EVAL_DESIGN 3절).
- 해설생성기 본문 형식으로 작성한 후속 3건에서 라벨 근거를 인용할 단계·문단 식별 방식.
