# [강의 2] 도메인 발견과 미니 온톨로지 — 산출물 작성 지침

> 공통 예제 **단골**(AI 맛집 추천, 예약 비서)이 이 산출물을 실제로 어떻게 채웠는지 보고 **같은 자리에 우리 팀 것**을 채운다.

> **누가 쓰는가** — 인터뷰와 관찰은 대신 시킬 수 없고, 로그는 이후 모든 판정의 기준이므로 사람이 쓴다. 온톨로지는 AI가 전사에서 명사와 동사, 태그, 클래스 후보를 뽑아도 되지만 **대표어, 경계, `evidence:`는 사람이 결정하고 승인한다.

> 파일 이름은 팀 규칙에 맞게 바꿔도 되지만 **저장 위치는 맞춘다** — 채점과 리뷰 때 이 경로를 본다. 저장소 전체 구조는 `00_README.md`의 "저장소 표준 구조"를 본다.

## A. 인터뷰 프로토콜

### 📘 단골 예시

- **대상(누구를, 왜)**: 여럿이 모이는 약속의 장소를 실제로 정해 본 직장인과 대학원생. 결정을 직접 내린 사람이라야 과거 행동을 재구성할 수 있다.
- **알아내려는 것(가설)**: 식당 선택의 진짜 비용은 "정보 부족"이 아니라 **결정 피로와 일행 제약 조율**이며, 사람들은 결국 "늘 가던 데"로 회귀한다.
- **질문 5개 — 과거 행동을 묻는 형태로**
  1. 마지막으로 여럿이 갈 식당을 직접 정했던 때 얘기를 들려주세요. — 과거의 구체적 사건으로 시작
  2. 그때 어떻게 찾았어요? 어떤 앱을 썼고 시간은 얼마나 걸렸어요? — 현재 고용된 대안과 실제 비용
  3. 그 과정에서 제일 번거로웠던 건 뭐였어요? — 겪은 경험에서 나오는 페인
  4. 일행 중 못 먹는 게 있는 사람이 있었나요? 그땐 어떻게 했어요? — 제약 조율의 우회로
  5. 결국 어디로 갔고 왜 거기였어요? — 말이 아닌 최종 행동
- **피해야 할 것**: 미래, 가정, 유도 질문, 내 해결책 설명
  - ❌ "맛집 추천 앱 있으면 쓰실래요?" — 미래, 가정, 유도. "네 좋죠"는 정보가 아니다.
  - ✅ "지난번 약속 장소는 어떻게 정하셨어요?" — 과거의 실제 행동.
- **원칙**: 인터뷰가 끝나도 상대는 우리 아이디어를 모른다. 우리 팀 아이디어를 얘기하지 않는다.

### 💬 왜 이렇게 썼나

- **대상을 "직장인"이 아니라 "장소를 직접 정해 본 직장인"으로 좁혔다.** 결정을 안 해 본 사람은 과거를 재구성할 수 없어 가정으로 답한다. 대상 정의에 **행동 조건**이 들어가야 Mom Test가 성립한다.
- **가설을 반증 가능하게 썼다.** "사람들은 맛집 찾기가 불편하다"는 반증할 수 없다. "정보 부족이 아니라 결정 피로가 비용이다"는 인터뷰로 틀릴 수 있다 — 그래서 쓸모 있다.
- **질문 5개가 하나의 사건을 따라간다.** 사건 회상(1) → 사용한 도구와 비용(2) → 페인(3) → 우회로(4) → 최종 행동(5). 주제를 흩뿌린 5개 질문보다 한 사건을 파고드는 5개가 훨씬 많이 건진다.
- **질문마다 "무엇을 알아내려는 질문인지"를 한 줄씩 달았다.** 이 줄이 없으면 질문지가 그냥 설문지가 된다.

🔁 **반드시 달라지는 곳** — 대상, 가설, 질문 5개 전부. 우리 제품의 사용자가 실제로 하는 행동에서 나와야 한다.
🧩 **따라 해도 되는 곳** — "한 사건을 따라가는 5문항" 구조, 질문마다 의도를 병기하는 방식, ❌/✅ 대조로 유도 질문을 걸러내는 점검 습관.

**도출된 페인 (누적)**

1. **결정 피로** [문제] — 반복 검색과 비교로 30분 이상 소모, 결국 익숙한 곳으로 회귀 (로그 1, 5, 9)
2. **일행 제약 조율** [제약] — 비건, 할랄 등 식이제약이 섞이면 후보 급감, 확인 비용 발생 (로그 1, 7)
3. **리뷰 불신** [문제] — 광고, 조작 리뷰를 눈으로 거를 수 없음 (로그 2, 10)
4. **분위기와 상황 정보 부재** [제약, 실패 유형] — mood와 occasion이 검색 축에 없음. 기대와 다른 결과(조용한 데를 골랐는데 시끄러움)와 같은 리스트의 재사용 실패가 여기서 나옴 (로그 3, 8)
5. **예약 절차의 수작업** [우회로] — 인원, 시간대, 잔여 좌석 확인이 반복 통화 (로그 1, 6)

> 범주 표기는 [문제 / 목표 / 우회로 / 제약 / 실패 유형] 중 해당하는 것을 쓴다. "목표"는 페인 목록이 아니라 아래 D절 Job Story에서 다룬다.

### 💬 왜 이렇게 썼나

- **인용이 요약이 아니라 그 사람의 말 그대로다.** "검색이 오래 걸린다더라"로 적으면 근거가 사라진다. "30분 넘게 오가다 그냥 늘 가던 데로 갔죠"에는 시간, 행동, 결과가 함께 들어 있다. 뒤에서 온톨로지 항목이 이 문장 하나로 정당화된다.
- **한 로그가 여러 페인을 낳아도 된다.** 로그 1은 식이제약, 결정 피로, 회귀, 예약 수작업 네 가지를 동시에 준다. 억지로 1:1로 나누지 않는다.
- **대상 옆에 괄호로 역할을 적었다.** "직장인 A"만으로는 나중에 이 사람이 왜 그렇게 말했는지 복원이 안 된다. (33, 동기 모임 주최)가 맥락을 붙든다.
- **태그는 요약이 아니라 색인이다.** `전화확인`이 로그 1, 6, 7, 9에 반복해서 붙는 것을 보고 "예약 절차의 수작업"이라는 페인이 나왔다. 태그를 먼저 붙이고 범주는 나중에 묶는다(오픈 코딩 → 축 코딩). 태그가 원문을 대신하게 두지 않는다 — 태그를 짚으면 로그 번호로, 로그 번호를 짚으면 인용 원문으로 돌아가야 한다.
- **페인마다 범주를 달았다.** 문제, 우회로, 제약, 실패 유형은 온톨로지에서 서로 다른 곳으로 간다 — 제약은 속성과 절대 규칙으로, 우회로는 관계와 기능 요구로, 실패 유형은 수용 기준의 실패 조건으로.
- **페인 목록마다 로그 번호를 달았다.** 이 번호가 곧 E절 `evidence:`의 원천이다. 여기서 번호를 안 달면 온톨로지에서 근거를 만들어 내게 된다.
- **부정적 신호도 남겼다.** 로그 8("같은 리스트가 안 통해요")은 우리 가설을 부분적으로 흔든다. 이런 로그를 지우지 않는 것이 발견의 질을 보여 준다.

🔁 **반드시 달라지는 곳** — 대상, 인용, 페인 전부. 인용은 실제로 들은 말이어야 한다(대화 기록이나 녹취 메모에서 옮긴다).
🧩 **따라 해도 되는 곳** — 표의 6개 열 구성, 관찰 사실 중심의 짧은 태그 표기, 로그 번호를 근거 ID로 쓰는 방식, 페인 목록에 범주와 로그 번호를 병기하는 방식.

## C. 워크플로 관찰 기록

> 인터뷰는 "말한 것"이고 관찰은 "한 것"이다. 응답자는 습관이 된 조작을 설명하지 못하므로, 최근 사례를 그 자리에서 시연하거나 화면 공유로 재현하게 한다. 관찰 기록에도 **관찰 번호**를 매기고, 온톨로지 `evidence:`에는 로그 번호와 함께 관찰 번호를 쓸 수 있다.

### 📘 단골 예시 (1건)

**관찰 1** — 대상: 직장인 A (로그 1의 응답자) / 일시: 3/9 인터뷰 직후 / 방법: 화면 공유로 "지난주 동기 모임 장소 찾기"를 처음부터 재현 (약 20분)

| 관찰 항목 | 관찰 내용 (본 것만 적는다) | 스펙 후보 (무엇으로 변환되는가) |
|---|---|---|
| 단계와 도구 | ① 지도 앱에서 "강남 비건" 검색 → ② 후보 3곳의 이름을 블로그 검색창에 하나씩 입력 → ③ 리뷰 확인 후 다시 지도 앱으로 복귀 → ④ 메신저로 일행에게 후보 2곳 링크 전송 → ⑤ 식당에 전화해 여섯 명 자리 확인 → ⑥ 결국 늘 가던 식당으로 결정 | 연동 환경: 지도, 블로그, 메신저가 실제 작업 도구. 추천 결과는 링크로 공유 가능해야 함 |
| 전환(Handoff) | ②에서 식당명을 지도 앱에서 복사해 블로그에 재입력 (3회 반복) / ④에서 후보를 메신저에 다시 옮겨 적음 | 후보 비교와 근거(리뷰)를 한 화면에 모으는 것이 핵심 요구사항 |
| 우회로(Workaround) | ⑤ 잔여 좌석과 시간대를 전화로 확인 / 비건 가능 여부를 메뉴에서 못 찾아 리뷰 본문을 검색해 확인 | `Reservation`(party_size, time_slot)과 `Menu.dietary_flags`가 필요한 이유. 예약은 목(mock) 처리 |
| 멈칫(Hesitation) | 리뷰 페이지에서 광고 여부를 가리려고 같은 페이지를 두 번 스크롤 / 후보를 두고 "여기 괜찮나…" 하며 12초 정지 후 지도 앱으로 되돌아감 | 추천에 근거를 함께 제시해야 할 이유. 결정까지 걸리는 시간이 이후 Evals 지표 후보 |

- 진술과 관찰의 차이: 로그 1에서 A는 "30분 넘게 오갔다"고 말했지만, 재현에서는 도구 전환이 6회, 재입력이 4회였다. 시간이 아니라 **전환 횟수**가 식당을 찾는 작업(Job) 비용의 실체다.

### 💬 왜 이렇게 썼나

- **본 것과 해석을 열로 갈랐다.** "관찰 내용" 열에는 동작과 횟수만 적고, 그것이 무엇을 뜻하는지는 "스펙 후보" 열에 따로 적었다. 두 열을 섞으면 관찰이 아니라 감상이 된다.
- **네 항목으로 구분한다.** 단계와 도구는 연동해야 할 환경으로, 전환은 핵심 기능 요구로, 우회로는 백로그 우선순위로, 멈칫은 나중에 측정할 지표로 간다. 항목마다 활용될 곳이 다르기 때문에 네 항목으로 따로 묶는다.
- **진술과 관찰이 어긋난 지점을 남겼다.** "30분"이라는 진술은 기억이고, "전환 6회"는 관찰이다. 어긋남 자체가 발견이다.
- **관찰 1건이면 시작으로 충분하다.** 발견 게이트의 정량 요건은 로그 10건이고, 관찰은 로그의 응답자 중 재현 가능한 사람에게 부탁한다. 팀당 2~3건이면 패턴이 보인다.

🔁 **반드시 달라지는 곳** — 대상, 단계, 도구, 전환 지점, 우회로, 멈칫 전부. 우리 사용자가 실제로 쓰는 도구와 손이 멈춘 순간에서 나와야 한다.
🧩 **따라 해도 되는 곳** — 관찰 4항목 표, "본 것 / 스펙 후보" 두 열 분리, 단계에 번호를 매겨 전환과 멈칫이 어느 단계에서 났는지 가리키는 방식, 관찰 번호를 근거 ID로 쓰는 규약.

### ✍️ 우리 팀

**관찰 1** — 대상: ____ (로그 __의 응답자) / 일시: ____ / 방법: [현장 시연 / 화면 공유 재현 / 기존 작업물 역추적] (약 __분)

| 관찰 항목 | 관찰 내용 (본 것만 적는다) | 스펙 후보 (무엇으로 변환되는가) |
|---|---|---|
| 단계와 도구 | ① ____ → ② ____ → ③ ____ | ____ |
| 전환(Handoff) | ____ (단계 번호와 횟수) | ____ |
| 우회로(Workaround) | ____ | ____ |
| 멈칫(Hesitation) | ____ (단계 번호, 지속 시간이나 반복 횟수) | ____ |

- 진술과 관찰의 차이: ____

## D. 핵심 Job Story

> 로그와 관찰이 쌓이면 사용자가 '고용하려는 일'을 한 문장으로 고정한다. 이 문장이 강의 4 스펙의 기능 시나리오로 넘어가고, 온톨로지에서 이 문장을 자기 어휘만으로 다시 쓸 수 있어야 한다. 팀당 핵심 Job Story는 1개, 많아도 2개다.

### 📘 단골 예시

**핵심 Job Story (단골)**

> 여럿이 갈 약속 장소를 내가 정해야 할 때, 나는 일행의 제약(식이제약, 예산, 지역, 시간)을 만족하는 식당을 근거와 함께 빠르게 고르고 싶다. 그래서 검색을 반복하지 않고 예약까지 끝낼 수 있도록. (로그 1, 4, 5, 6, 7)

| 요소 | 내용 | 근거 |
|---|---|---|
| 상황(트리거) | 모임 주최자가 되어 장소를 정해야 하는 시점. 일행 중 제약(비건, 할랄, 예산 상한)이 있을 때 문제가 발현 | 로그 1, 4, 7 |
| 기능적 Job | 제약을 만족하는 식당을 고르고 자리를 확보 | 로그 1, 5, 6 |
| 감정적 Job | "실패가 없는" 선택이라는 확신. 잘못 고르면 모임을 망친다는 부담 회피 | 로그 1, 3 |
| 사회적 Job | 일행에게 배려 있는 주최자로 보이기(못 먹는 사람이 없게) | 로그 1, 7 (심층 질의로 확인) |
| 현재 고용된 대안 | 지도 앱, 블로그, 리뷰 반복 탐색. 결국 "늘 가던 데" | 로그 1, 5, 관찰 1 |

**전환의 네 가지 요소**

| 전환 요소 | 내용 | 근거 |
|---|---|---|
| Push (기존 대안의 불만) | 30분 이상 검색해도 확신이 서지 않음. 세 군데 전화를 돌림 | 로그 1, 6 |
| Pull (새 해결책의 매력) | 제약을 만족하는 한 곳을 근거와 함께 추천받고 예약까지 끝남 — **아직 가설**, 인터뷰로 검증되지 않음 | (가설) |
| Anxiety (새 해결책의 불안) | 추천의 근거가 광고 리뷰면 믿을 수 없음 | 로그 2, 10 |
| Habit (관성) | "거긴 실패가 없으니까" — 늘 가던 데로 회귀 | 로그 1 |

### 💬 왜 이렇게 썼나

- **상황, 동기, 기대 결과가 각각 로그로 추적 가능하다.** "빠르게"는 로그 1의 30분에서, "제약을 만족하는"은 로그 1, 4, 5, 7에서, "예약까지"는 로그 6에서 나왔다. 로그 번호를 붙일 수 없는 Job 스토리는 사용자의 Job이 아니다.
- **Pull만 "가설"로 표시했다.** 나머지 세 힘은 과거 행동에서 나오지만 Pull은 아직 없는 제품의 매력이라 인터뷰로 확인할 수 없다. 이것을 사실처럼 적는 순간 Mom Test가 무너진다.
- **Habit이 진짜 경쟁자다.** "늘 가던 데"는 실패가 없다는 확신을 준다. 새 해결책이 이 관성을 이기려면 Push와 Pull의 합이 Anxiety와 Habit의 합보다 커야 하고, 그래서 추천에 근거(리뷰, 메뉴)를 붙이는 것이 제품의 핵심이 된다.
- **감정적 Job과 사회적 Job은 심층 질의로 확인했다.** 자발적으로 나오지 않는 층이라 "그때 무엇이 제일 걱정됐나", "일행이 어떻게 생각할지 신경 쓰였나"를 따로 물었다. 그 답이 로그에 남아야 근거가 된다.
- **온톨로지가 이 문장을 다시 쓸 수 있는지 확인했다.** `RequestContext`(상황과 제약) → `Restaurant`, `Menu`, `Review`(근거) → `Reservation`(예약까지). 한 요소라도 온톨로지 어휘로 옮겨지지 않으면 온톨로지에 빈 곳이 있는 것이다.

🔁 **반드시 달라지는 곳** — Job Story 문장, 세 차원, 네 가지 전환 요소, 현재 고용된 대안 전부. 우리 로그에서 나와야 한다.
🧩 **따라 해도 되는 곳** — "[상황]일 때, 나는 [동기]하고 싶다, 그래서 [기대 결과]할 수 있도록" 한 문장 골격, 요소별 근거 표, 네 힘 표에서 Pull을 가설로 따로 표시하는 규약, 온톨로지로 되쓰기 검증.

### ✍️ 우리 팀

**핵심 Job Story**

> ____일 때, 나는 ____하고 싶다. 그래서 ____할 수 있도록. (로그 __, __)

| 요소 | 내용 | 근거 |
|---|---|---|
| 상황(트리거) | ____ | 로그 __ |

## E. 미니 온톨로지

> 온톨로지가 정의하는 것은 **클래스**(개념 유형)다. 개별 사례(특정 식당이나 특정 리뷰)는 **인스턴스**이자 데이터이므로 여기서 정의하지 않는다.

### 📘 단골 예시

먼저 로그에서 어휘를 뽑는 중간 단계를 거쳤다.

- 반복된 명사 → 클래스, 속성 후보: 늘 가던 데/단골집 → `Restaurant`, 메뉴, 가격 → `Menu`, 리뷰 → `Review`, 일행, 인원 → `User`, `party_size`, 자리 잡기 → `Reservation`, 조건 묶음 → `RequestContext`
- 반복된 동사 → 관계 후보: 못 먹는다(거른다), 찾고 거른다(매칭), 자리를 잡는다(예약한다)
- 동의어 통합: '늘 가던 데' = '아는 데' = '단골집' → `Restaurant`
- 범위 밖: 결제 / POS 연동 / 배달

```yaml
# 단골 미니 도메인 온톨로지 (강의 2 산출물)
# evidence: 는 B절 인터뷰 로그의 번호(관찰 기록은 '관찰 N'). 근거로 역추적되지 않는 항목은 두지 않는다.
# 규칙: relations의 대상은 반드시 이 파일에 정의된 클래스여야 한다(미정의 클래스 참조 금지).
version: 1
classes:
  Restaurant:
    description: 추천과 예약의 대상이 되는 식당
    evidence: [로그 1, 로그 5, 로그 8]   # '늘 가던 데' = '아는 데' = '단골집' → 대표어 Restaurant
    attributes:
      id: {type: string, key: true}
      name: {type: string}
      area: {type: string, examples: [강남, 홍대, 성수, 이태원], evidence: [로그 5]}
      price_range: {type: int, range: [1, 4], evidence: [로그 4]}
      mood_tags: {type: list, examples: [조용한, 활기찬, 데이트, 모임, 혼밥, 분위기], evidence: [로그 3]}
    relations:
      - has: Menu
        evidence: [로그 7, 로그 9]
      - has: Review
        evidence: [로그 2, 로그 10]
  Menu:
    description: 식당의 메뉴 항목
    evidence: [로그 7, 로그 9]
    attributes:
      name: {type: string}
      price: {type: int, evidence: [로그 9]}
      dietary_flags: {type: list, examples: [vegan, vegetarian, halal, gluten_free], evidence: [로그 1, 로그 7]}
    relations:
      - belongs_to: Restaurant
        evidence: [로그 9]
  Review:
    description: 사용자 리뷰. 신뢰할 수 없는 외부 입력으로 취급(인젝션 방어).
    evidence: [로그 2, 로그 10]
    attributes:
      author: {type: string}
      rating: {type: float, range: [0, 5]}
      text: {type: string, note: "데이터로만 다룬다 — 명령으로 실행 금지", evidence: [로그 10]}
    relations:
      - about: Restaurant
        evidence: [로그 2]
      - mentions: Menu
        evidence: [로그 7, 로그 9]
  User:
    description: 추천을 받고 예약하는 사용자
    evidence: [로그 1, 로그 8]
    attributes:
      preferences: {type: list, evidence: [로그 3, 로그 8]}
      dietary_constraints: {type: list, examples: [vegan, halal, gluten_free], evidence: [로그 1, 로그 7]}
    relations:
      - makes: Reservation
        evidence: [로그 1, 로그 6]
  Reservation:
    description: 예약(목 처리 — 결제, POS 연동 없음)
    evidence: [로그 1, 로그 6]
    attributes:
      party_size: {type: int, evidence: [로그 1]}
      time_slot: {type: string, evidence: [로그 6]}
      status: {type: enum, values: [pending, confirmed, cancelled], evidence: [로그 6]}
    relations:
      - for: Restaurant
        evidence: [로그 1]
      - by: User
        evidence: [로그 1]
  RequestContext:
    description: 사용자 발화를 파싱한 구조화 결과(구조화 출력의 대상)
    evidence: [로그 1, 로그 4, 로그 5, 로그 8]
    attributes:
      area: {type: string, evidence: [로그 5]}
      party_size: {type: int, evidence: [로그 1]}
      vibe: {type: list, evidence: [로그 3]}
      dietary: {type: list, evidence: [로그 1, 로그 7]}
      occasion: {type: string, evidence: [로그 8]}
      budget: {type: int, evidence: [로그 4]}
      time: {type: string, format: "HH:MM(24h)", note: "발화에 나온 희망 시각. 확정된 슬롯은 Reservation.time_slot", evidence: [로그 6]}
# 범위 밖(명시): 결제 / POS 연동 / 배달
# 핵심 흐름: RequestContext --(매칭)--> Restaurant --(근거: Menu, Review)--> Reservation
```

### 💬 왜 이렇게 썼나

- **클래스가 6개.** 단골은 로그에서 여러번 등장한 명사를 남겼다.
- **모든 클래스, 속성, 관계에 `evidence:`가 붙어 있다.** 이것이 추적 가능하게 하는 핵심 장치다. `mood_tags`가 있는 이유는 "있으면 좋을 것 같아서"가 아니라 로그 3이 있어서다. **역추적되지 않는 항목은 지우는 것이 원칙이다**
- **`relations`의 대상이 전부 이 파일에 정의된 클래스다.** 관계를 쓸 때마다 "이 이름이 위에 클래스로 있나"를 확인한다. 없으면 클래스로 추가하거나 관계를 지운다.
- **동의어를 대표어 하나로 합쳤다.** 메뉴를 `Menu`로 통일하고 `Dish`같은 동의어/유사어는 쓰지 않는다. 대표어가 흔들리면 스펙, 코드, 테스트에서 서로 다른 이름이 나타나 개발 및 검증 자체를 흔들 수 있다.
- **`RequestContext.time`과 `Reservation.time_slot`을 다른 필드로 두고 note로 구분을 적었다.** 이름이 비슷한 두 개념은 반드시 note로 갈라 둔다. 강의 3에서 스키마로, 강의 5에서 테스트로 그대로 넘어간다.
- **범위 밖을 명시했다.** 결제, POS, 배달은 로그에 거의 없었고 이번 개발 범위에서는 제외한다. 안 만들 것도 스펙에 명시하는 것이 바람직하다.
- **Review를 "신뢰할 수 없는 외부 입력"으로 미리 규정했다.** 로그 10에서 나온 판단인데 레드티밍 강의(리뷰 인젝션)까지 이어진다. 보안은 나중에 추가로 구현하는 것 보다  온톨로지에서 부터 시작하는 것이 이상적이다.

🔁 **반드시 달라지는 곳** — 클래스 이름, 속성, 관계, 범위 밖 전부. 우리 로그에서 반복된 명사와 동사로만 만든다.
🧩 **따라 해도 되는 곳** — YAML 골격(`version`/`classes`/`description`/`evidence`/`attributes`/`relations`), `evidence:`를 세 층(클래스, 속성, 관계) 전부에 다는 규약, 맨 아래 "범위 밖"과 "핵심 흐름"을 코멘트로 적어 두는 것, 해석이 헷갈릴 수 있는 필드에 note를 다는 습관.

### ✍️ 우리 팀

먼저 로그에서 어휘를 뽑는다.

- 반복된 명사 → 클래스 후보: ____
- 반복된 동사 → 관계 후보: ____
- 동의어 통합: ____ = ____ → 대표어 `____`
- 범위 밖: ____

```yaml
version: 1
classes:
  <클래스명>:
    description: <이 개념이 무엇인지 한 줄>
    evidence: [로그 _, 로그 _]                       # ← ① 클래스의 근거 (필수)
    attributes:
      <속성명>: {type: <타입>, examples: [<예시>], evidence: [로그 _]}   # ← ② 속성의 근거
    relations:
      - <관계(동사)>: <대상 클래스>                   # ← 반드시 이 파일에 정의된 클래스
        evidence: [로그 _]                           # ← ③ 관계의 근거
# 범위 밖(명시): <이번 제품에서 다루지 않을 개념>
# 핵심 흐름: <클래스> --(동사)--> <클래스> --(동사)--> <클래스>
```

## 자가 점검 체크 리스트

- [ ] 인터뷰 로그가 충분하고(10건 이상) 인용이 실제로 들은 말인가
- [ ] 질문이 과거 행동을 묻는가 (미래, 가정, 유도 질문이 섞이지 않았는가)
- [ ] 로그마다 태그가 붙어 있고, 페인마다 범주와 로그 번호가 있는가
- [ ] 워크플로 관찰 기록이 1건 이상이고 "본 것"과 "스펙 후보"가 열로 분리되어 있는가
- [ ] 핵심 Job Story의 상황, 동기, 기대 결과가 각각 로그 번호로 연결되고, Pull이 가설로 표시되어 있는가
- [ ] 온톨로지 어휘만으로 Job Story를 다시 쓸 수 있는가
- [ ] 클래스는 전부 로그에서 반복된 명사인가
- [ ] **모든 클래스, 속성, 관계에 `evidence:`가 있고 그 번호가 우리 로그에 실제로 있는가**
- [ ] **`relations`의 대상이 전부 이 파일에 정의된 클래스인가**
- [ ] 동의어가 대표어 하나로 합쳐졌는가
- [ ] 범위 밖이 명시되어 있는가
- [ ] 팀원 누구라도 임의의 항목을 짚었을 때 "왜 넣었는지"를 로그로 설명할 수 있는가

## 루브릭 (발견 게이트로 이어짐)

- 인터뷰 내용이 과거 행동 기반인가 (유도 질문 감점) … 40%
- 페인이 인용과 관찰로 뒷받침되는가 … 30%
- 온톨로지 클래스, 속성, 관계의 정확성과 유용성 … 30%

> 위 세 항목 모두에서 **근거 역추적**이 실질적 평가 기준이다. 그럴듯하지만 로그로 연결되지 않는 산출물은 좋은 평가를 받을 수 없다.
