# 산출물 작성 지침과 루브릭

이 폴더의 `강의NN_..._작성지침.md`가 **각 강의에서 무엇을 만들어 저장소 어디에 두어야 하는지**를 정한다. 매주 강의가 끝나면 해당 지침을 받아 그 주의 개념을 자기 팀 제품에 적용한 산출물을 만든다.

## 각 지침은 다음과 같다

1. **이번 강의에서 만드는 것** — 산출물 목록 표. 파일, 형식, 무엇을 담는가, **저장소 위치**, 선행 산출물, 이후 어디에 쓰이나.
2. **각 세션은 다음 내용으로 구성 **

| 표시 | 뜻 |
|---|---|
| 📘 **단골 예시** | 공통 예제 단골이 그 자리를 실제로 채운 내용. 분량과 구체성의 기준. |
| 💬 **왜 이렇게 썼나** | 그 예시의 판단 근거. 채점 기준과 직결된다. |
| 🔁 **반드시 달라지는 곳** | 도메인이 다르면 달라질 수밖에 없는 자리. |
| 🧩 **따라 해도 되는 곳** | 형식과 표기 규약. 오히려 맞추는 편이 좋다. |
| ✍️ **우리 팀** | 여러분이 채우는 칸. |

3. **자가 점검 체크 리스트**
4. **루브릭** — 중요도 비중(절대 기준 아님).

## 지켜야 할 것

- **저장 위치는 맞춘다.** 파일 이름은 팀 규칙에 맞게 바꿔도 되지만 경로는 지침의 표를 따른다. 평가와 리뷰 때 이 경로를 본다.
- **형식은 가져다 쓰되 내용은 스스로 만든다.** 🧩로 표시된 규약(evidence 표기, 스키마 골격, AC 번호 관리 등)은 맞추는 편이 좋다. 🔁로 표시된 내용은 우리 팀 인터뷰와 온톨로지에서 나와야 한다.
- **모든 항목은 역추적이 가능해야 한다.** 임의의 항목을 짚었을 때 그것이 우리 팀 로그 번호나 AC 번호로 연결되어야 한다.

# 산출물은 어떻게 이어지는가

(아래 산출물 지도는 참고용이며 변경될 수 있음)
![한 학기 산출물 지도](산출물_지도.svg)

> 그림 파일: `산출물_지도.svg` (같은 폴더). 강의 1에서 이 지도를 먼저 보고 시작한다. 학기 중 세부는 조정될 수 있지만 **연결 구조는 바뀌지 않는다.**

## 1. 한 줄 요약

**사람은 기준을 만들고, AI는 그 기준을 만족시킨다.**

이 과목에서 만드는 문서는 "제출용 서류"가 아니다. **다음 단계의 AI 에이전트가 읽는 입력**이고 동시에 **그 에이전트의 결과물을 판정하는 잣대**다. 그래서 산출물 순서가 중요하다.

## 2. 누가 만드는가 — 세 부류

| 구분 | 무엇이 여기 속하나 | 왜 그런가 |
|---|---|---|
| **사람이 정한다** | 인터뷰 로그, 문제 정의서, 스펙의 **수용 기준(AC)**, AGENTS.md의 절대 규칙, 골든 케이스, evals 지표 | 모두 **기준**이다. 기준을 AI가 정하면 그 기준으로 AI를 검증할 수 없다. 인터뷰는 AI에게 대신 시킬 수도 없다. |
| **사람이 뼈대, AI가 초안** | 온톨로지, 출력 스키마, 파싱 프롬프트, 스파이크, 아키텍처, `rag.yaml`, 평가 데이터셋 | AI가 후보를 빠르게 뽑아 주고 **대표어, 경계, 값은 사람이 결정한다.** 결정의 근거를 설명할 수 있어야 내 것이다. |
| **AI가 만들고 사람이 검증** | 구현 코드, 도구, evals 러너 | 완료 기준이 **이미 데이터로 있어서** 기계가 판정할 수 있다. |

> **완료 기준이 데이터나 문서로 명시되어 있는 것만 AI에게 온전히 맡길 수 있다.** 앞의 문서들이 먼저인 이유가 이것이다. 골든 케이스 없이 "랭킹 함수 만들어 줘"라고 하면, 무엇이 완성인지 아무도 설명할 수 없는 코드가 나온다.

## 3. 각 산출물은 이후 단계와 어떻게 연결되는가?

| 산출물 | 세부 항목 | 연결 되는 부분 |
|---|---|---|
| 강의 2 인터뷰 로그 | **로그 번호** | 온톨로지 `evidence:` / 강의 4 문제 정의서의 증거 |
| 강의 2 관찰 기록과 Job Story | **관찰 번호, 기능 시나리오 한 문장** | 온톨로지 `evidence:` / 강의 4 스펙의 기능 시나리오 |
| 강의 2 온톨로지 | **클래스 대표어, 요청 컨텍스트** | 강의 3 출력 스키마 / 강의 4 AGENTS.md 용어집과 데이터 모델 |
| 강의 3 출력 스키마 | **구조 계약(필드, 타입, enum)** | 강의 5 골든 케이스의 `context` / 강의 6 도구 시그니처 |
| 강의 4 스펙의 AC | **완료 기준** | 강의 5 골든 케이스 / 강의 7 evals 지표 |
| 강의 4 AGENTS.md | **상시 규칙** | 이후 모든 위임 작업 |
| 강의 5 골든 케이스 | **결정 층 판정** | 강의 6 구현 검증 / CI |
| 강의 6 관측 로그 | **측정 대상** | 강의 7 evals / 12주 오류 분석 |

## 4. 이 문서들이 제품의 일관성과 품질을 담보하는 방식

### ① 어휘 일관성

`온톨로지 대표어 → AGENTS.md 용어집 → 출력 스키마 → 함수 시그니처 → 테스트와 evals`

같은 개념을 끝까지 같은 이름으로 부른다. AI 에이전트는 세션 기억이 없어 매번 이름을 새로 추론한다 — 오늘 `Restaurant`, 내일 `Store`, 모레 `Place`. 이름이 흔들리면 스키마/테스트/코드가 점점 더 어긋나게 된다. AGENTS.md의 용어집이 **`CLAUDE.md`에서 `@AGENTS.md`로 끌어올려 매 작업마다 함께 읽히는 최소 어휘**로서 이 흔들림을 막는다. 반드시 'import'를 해야 한다. 그렇지 않으면 않으면 파일만 있고 읽히지는 않는다 — `/context`로 확인한다.

### ② 근거 역추적

`인터뷰 로그 번호 → 온톨로지 evidence → 문제 정의서 증거 → 스펙의 범위`

모든 항목이 **"왜 여기 있나"**에 답할 수 있다. 그럴듯하지만 근거가 없는 산출물은 AI가 몇 초 만에 만들어 줄 수 있다. 그러나 역추적 연결 고리를 통해 근거 없는 산출물을 가려낼 수 있다.

### ③ 완료 기준의 자동 판정

`수용 기준(AC) → 골든 케이스(결정 층) → evals(통계 층) → 오류 분석 → 개선`

**'완료 조건'을 사람의 주관적 판단이 아니라 기계가 판정한다.** 그래서 AI에게 안심하고 위임할 수 있고 개선이 실제로 '개선'인지 정량적으로 확인할 수 있다. AC가 테스트로 옮겨지지 않으면 이 고리가 끊기고 그때부터 일관성있게 품질을 판단할 수 없게 된다.

## 5. 그래서 산출물 순서가 중요하다

앞 문서가 없으면 다음 문서는 근거 없이 채워진다. 그 결과는 대개 게이트에서 **"왜 이렇게 했나"에 답하지 못하는 것**으로 드러난다. 반대로, 앞 문서를 고쳤으면 뒤 문서도 같이 고친다.

## 저장소 표준 구조

저장소 표준 구조는 다음과 같다. 각 팀은 이 문서를 확인하자마자 바로 이와같은 구조로 저장소에 골격을 만들어 두기 바란다. 지침에 따른 산출물은 반드시 해당 위치에 두도록 한다. 

```
<팀-저장소>/
  AGENTS.md                          # 강의 4 — 도메인 용어집, 절대 규칙, 완료의 정의
  docs/
    research/interviews.md           # 강의 2 — 인터뷰 프로토콜과 로그
    ontology.yaml                    # 강의 2 — 미니 온톨로지
    PROBLEM.md                       # 강의 4 — 문제 정의서
    SPEC.md                          # 강의 4 — 제품 스펙(SDD)과 수용 기준(AC)
    spikes/YYYY-MM-DD_<가설>.md      # 강의 4 — 기술 타당성 스파이크
    ARCHITECTURE.md                  # 강의 6 — 아키텍처 설계서
    prompts/delegation_examples.md   # 강의 5 — 위임 프롬프트와 검증 루프 기록
  src/<패키지>/
    schemas/<클래스>.schema.json     # 강의 3 — 출력 스키마
    prompts/parse_query.md           # 강의 3 — 파싱 프롬프트
    tools/                           # 강의 6 — 도구 구현
  config/rag.yaml                    # 강의 6 — RAG 설정
  tests/
    harness/golden_cases.yaml        # 강의 5 — 골든 케이스(데이터)
    test_<기능>_golden.py            # 강의 5 — 골든 테스트
  evals/
    evalset.jsonl                    # 강의 7 — 평가 데이터셋
    README.md                        # 강의 7 — evals 설계
    judge_prompt.md                  # 강의 7 — judge 프롬프트
    run_evals.py                     # 강의 7 — 러너
    results/YYYY-MM-DD.json          # 강의 7 — 측정 기록
  data/seed/                         # 예시 데이터
```

## 파일 이름 규칙

- `강의NN_...` 의 **NN은 강의 자료의 일련번호**이며 학사 주차와는 무관하다(일정은 변동될 수 있다).
- `공통_...` — 강의 진도와 관계없이 상시 쓰는 지침. (현재 해당 파일 없음)
