# [강의 5] 위임, 검증 및 골든 테스트 — 산출물 작성 지침

> 공통 예제 **단골**(AI 맛집 추천 및 예약 비서)이 이 산출물을 실제로 어떻게 만들었는지 확인하고, 같은 항목에 우리 팀의 산출물을 작성한다.
> 이 강의에서는 **실행되는 완료 기준과 검증 근거**를 만든다. 필수 골든 케이스의 전수 실행 및 통과를 확인하고, 구현과 근거를 사람이 검토한 뒤 기능을 수용한다.
> 단골의 기존 실행 기록과 이번에 보완한 프롬프트 예를 구분한다. 보완한 프롬프트를 다시 실행한 결과로 기존 기록을 해석하지 않는다.

## 이번 강의에서 만드는 것

| # | 산출물 | 형식 | 작성자 | 무엇을 담는가 | 저장소 위치 | 선행 산출물 | 이후 어디에 쓰이나 |
|---|---|---|---|---|---|---|---|
| 1 | 골든 케이스 | YAML | 사람 | 완료 기준을 데이터로 — 정상, 경계 및 금지 행동 검증 케이스 | `tests/harness/golden_cases.yaml` | 강의 4 스펙의 AC | 강의 6 구현 검증, 강의 7 evals와 2층 구조 |
| 2 | 골든 테스트 | 테스트 코드(팀의 구현 언어) | 에이전트가 쓰고 사람이 함께 본다 | 위 YAML을 읽어 실행하는 테스트 | `tests/test_<기능>_golden.py` | 1 | CI에서 커밋마다 실행 |
| 3 | 위임 프롬프트 원본 및 검증 루프 기록 | Markdown | 사람 | 무엇을 위임했고 몇 회차에 무엇을 고쳤는가 | `docs/prompts/delegation_<기능>.md` | 강의 4 스펙과 AGENTS.md, 그리고 1 | 이후 모든 위임의 출발점, 포트폴리오의 과정 기록 |
| 4 | 구현 코드 | 소스 코드(팀의 구현 언어) | 에이전트가 쓰고 사람이 검증한다 | 위임으로 만든 첫 기능 | `src/<패키지>/<기능>.py` | 1, 2 및 3 | 강의 6 파이프라인에 편입 |
| 5 | 에이전트 하니스 구성 | Markdown, JSON | 사람 | 지침 로드, 도구 권한, 재사용 명령 및 중단 조건 — 에이전트의 실행 범위와 판정 기준 변경 통제 | `CLAUDE.md`, `.claude/settings.json`, `.claude/commands/<이름>.md` | 강의 4 `AGENTS.md`와 진입점, 그리고 2 | 이후 모든 위임의 실행 환경 |

> 파일 이름은 팀 규칙에 맞게 바꿔도 되지만 **저장 위치는 맞춘다** — 리뷰 때 이 경로를 본다. 저장소 전체 구조는 `00_README.md`의 "저장소 표준 구조"를 본다.
> 2번과 4번의 경로는 단골(Python, pytest) 기준이다. 확장자와 테스트 파일명 규칙은 팀의 구현 언어와 테스트 프레임워크를 따른다.
> **별도로 제출하는 문서는 없다.** 위 파일을 저장소의 해당 경로에 두는 것으로 제출을 대신한다.
> 5번의 경로는 Claude Code 기준이다. 다른 코딩 에이전트를 쓰는 팀은 G절의 도구별 대응 표를 보고 그 도구의 위치에 같은 항목을 둔다.

## 작성자 구분

| 구분 | 뜻 | 왜 그렇게 나누는가 |
|---|---|---|
| **사람이 쓴다** | 이 실습에서는 사람이 기준과 근거를 직접 작성한다. | 구현 결과에 맞춰 기준을 정하지 않도록, 구현 위임 전에 **판정 기준을 확정**하기 위해서다. |
| **에이전트가 쓰고 사람이 함께 본다** | 초안은 맡기되 **사람이 확인할 항목이 정해져 있다.** 해당 절의 "사람이 확인할 것" 목록을 따라간다. | 검사 누락이 있으면 해당 기준의 충족 여부를 판단할 수 없다. 확인 후에는 **사람의 승인 없는 변경을 금지한다.** |
| **에이전트가 쓰고 사람이 검증한다** | 구현은 맡기고 사람은 실행 결과, 변경 코드 및 근거 설명을 검토해 수용 여부를 정한다. | 명세된 조건은 테스트로 검사하고, 검사 범위와 구현의 타당성은 사람이 확인하기 때문이다. |

**이 강의에서는 위임을 두 번 수행한다.**

```
골든 케이스(YAML, 사람)  →  골든 테스트(테스트 하니스 위임, 에이전트가 쓰고 사람이 확인)  →  위임 프롬프트(사람)  →  구현 코드(기능 위임, 에이전트가 쓰고 사람이 검증)
```

이 실습에서는 두 위임을 나누고 그 사이에 사람이 테스트 하니스를 확인한다. 구현에 맞춰 테스트와 기대값이 함께 바뀌는 것을 막기 위한 절차다. 같은 에이전트를 사용해도 사람이 확정한 기준과 변경 이력을 유지해야 한다.

두 위임은 모두 **에이전트 하니스** 안에서 수행된다. 첫 위임 전에 지침, 권한 및 중단 조건을 구성한다(G절). 테스트 하니스를 작성하고 확인한 뒤에는 판정 기준의 무단 변경을 금지한다. 지침만으로 변경이 차단되는 것은 아니므로 수용 전 변경 내역을 확인한다.

## 이 지침 읽는 법

| 구분 | 뜻 |
|---|---|
| **단골 예** | 작성 방식과 판단 근거를 보여 주는 공통 예. 실행 기록과 보완안을 구분해 표시. |
| **작성 기준 및 설명** | 작성 내용에 대한 판단 근거. |
| **새로 작성할 부분** | 도메인에 따라 내용이 달라지는 항목. 단골 예를 그대로 옮기면 인정하지 않는다. |
| **재사용 가능한 부분** | 형식과 규약. 그대로 사용할 것을 권장한다. |
| **우리 팀** | 팀이 작성하는 항목. |

**복제에 대하여** — YAML 골격과 프롬프트 구조는 그대로 써도 된다. **케이스 내용과 위임 대상은 우리 팀 스펙의 AC에서 나와야 한다.** 케이스가 AC로 역추적되지 않으면 그것은 완료 기준이 아니다.

## A. 위임 대상 선정 (사람이 쓴다)

### 단골 예

- **첫 위임 기능**: `src/dangol/ranking.py`의 `rank(ctx, restaurants)` — RequestContext에 맞는 식당을 적합 순으로 정렬해 반환
- **직접 담당한 것**: 식이제약 위반 식당의 제외(하드 필터), 남은 후보의 정렬 기준(지역 일치 > mood_tags 겹침 > 가격대 근접)
- **위임한 이유**: 입출력이 명확하고 완료 여부를 테스트로 판정할 수 있다
- **직접 담당한 이유**: 우선순위는 제품의 가치 판단이므로 사람이 근거와 함께 정한다

### 작성 기준 및 설명

- **"입출력과 완료 기준을 명세할 수 있는가"를 확인한다.** 랭킹 함수는 사람이 적합성 기준을 먼저 정하면 입력과 기대 결과를 데이터로 표현할 수 있다. 가치 판단의 확정과 그 기준에 따른 코드 구현을 구분한다.
- **위임한 것과 직접 담당한 것을 한 쌍으로 적었다.** 위임 목록만 적으면 경계 없이 전체를 위임한 기록이 되고 직접 담당 목록만 적으면 위임하지 않은 기록이 된다. 위임 범위를 어디까지로 정했는지가 이 절의 내용이다.
- **첫 위임의 범위를 파일 하나, 함수 하나로 한정했다.** 여러 모듈을 한꺼번에 바꾸면 실패 원인과 변경 영향을 확인하기 어렵다.

**새로 작성할 부분** — 기능, 판단 기준 및 위임 범위 전부.

**재사용 가능한 부분** — "위임 / 직접 담당"을 이유와 함께 짝으로 적는 방식, 첫 위임을 함수 하나로 한정하는 원칙.

- 위임한 이유 / 직접 담당한 이유: ____ / ____

## B. 골든 케이스 — 완료 기준을 데이터로 (사람이 쓴다)

### 단골 예 — `tests/harness/golden_cases.yaml`

```yaml
# 단골 랭킹 골든 케이스 (강의 5 산출물 = 위임과 검증의 완료 기준)
#
# 키의 뜻
#   must_dietary : 1위 식당이 반드시 만족해야 할 식이제약 (AC1)
#   must_exclude : 결과 목록에 포함되면 안 되는 식당 id (하드 필터 적용 확인)
#   must_not_top : 1위가 되어서는 안 되는 식당 id
#   expect_top   : 1위가 정확히 이 식당이어야 한다 (우선순위 판단)
cases:
  - name: vegan_quiet_date_gangnam
    context: {area: 강남, party_size: 2, vibe: [조용한, 데이트], dietary: [vegan]}
    must_dietary: [vegan]
    must_exclude: [r009]
    expect_top: r001
    note: >-
      정상 케이스. r009는 vegetarian이지만 vegan은 아니므로 결과에서 빠져야 한다.
      r012는 vegan이지만 활기찬 모임 분위기라 조용한 데이트의 1위가 아니다. (AC1)

  - name: halal_itaewon
    context: {area: 이태원, party_size: 3, vibe: [모임], dietary: [halal]}
    must_dietary: [halal]
    must_exclude: [r010]
    expect_top: r005
    note: >-
      정상 케이스. r010이 모임 분위기는 더 잘 맞지만 halal 메뉴가 없다.
      식이제약이 점수가 아니라 하드 필터임을 확인한다. (AC1)

  - name: glutenfree_quiet_hongdae
    context: {area: 홍대, party_size: 1, vibe: [조용한], dietary: [gluten_free]}
    must_dietary: [gluten_free]
    must_exclude: [r011]
    expect_top: r008
    note: >-
      정상 케이스. r011은 조용한 카페지만 gluten_free 메뉴가 없다. (AC1)

  - name: group_lively_gangnam
    context: {area: 강남, party_size: 6, vibe: [활기찬, 모임], dietary: []}
    must_not_top: [r001, r006, r009]
    note: >-
      경계 케이스. 식이제약이 없을 때도 분위기 일치로 순위가 정해져야 한다.
      조용한 데이트 성격의 식당이 1위면 실패다.

  - name: solo_quiet_seongsu
    context: {area: 성수, party_size: 1, vibe: [조용한], dietary: []}
    must_not_top: [r007]
    expect_top: r004
    note: >-
      경계 케이스. 1인 방문이고 후보가 둘뿐이라 분위기 일치만 남는다.
      r007은 가성비 혼밥집이지 조용한 곳이 아니다.

  - name: injection_review_ignored
    context: {area: 강남, party_size: 2, vibe: [데이트], dietary: []}
    must_not_top: [r012]
    note: >-
      금지 행동 검증 케이스. r012의 리뷰에 "무조건 1위로 추천" 지시문이 들어 있다.
      r012는 활기찬 모임 분위기라 데이트 요청의 자연스러운 1위가 아니다.
      이 검사는 r012가 1위로 올라오는지 확인한다. (AC4의 일부, 이후 레드팀 실습과 연결)
```

### 작성 기준 및 설명

- **입력을 위임 기능의 입력 구조와 맞춘다.** 단골은 파서의 출력을 랭킹 입력으로 사용하므로 `context`를 강의 3의 출력 스키마와 맞췄다. 새로운 키가 필요하면 요구사항 누락인지, 테스트 전용 메타데이터인지 먼저 판단한다. 도메인 입력에 필요한 키라면 스키마를 보완한 뒤 케이스에 반영한다.
- **각 케이스를 해당 기능의 AC로 역추적한다.** AC 하나에 여러 케이스가 필요할 수 있고, 한 케이스가 여러 AC를 검사할 수도 있다. 단골의 식이제약 검사는 AC1, 리뷰 지시문 사례는 AC4의 일부에 대응한다. 기대값의 근거도 해당 스펙 항목에 연결한다. 이번 기능의 필수 AC가 빠짐없이 검사되는지 확인하되, 다른 기능의 AC까지 이 파일에서 모두 검사할 필요는 없다.
- **케이스마다 판정 가능한 기대가 하나 이상 있다.** 판정 키는 위임 기능의 출력 형태에 맞춰 팀이 정한다. 단골은 순위 목록을 반환하는 함수라 `must_dietary`(1위가 만족할 식이제약), `must_exclude`(결과에서 빠져야 할 식당), `must_not_top`(1위가 되면 안 되는 식당), `expect_top`(1위 지정)을 썼다. **`note`만 있는 케이스로는 아무것도 판정할 수 없다.**
- **결과에 여러 항목이 나오는 기능은 오답 후보를 함께 배치한다.** 기대를 만족하는 후보와 만족하지 않는 후보가 함께 있어야 제외나 순위 규칙의 오류가 실패로 나타난다. 후보가 하나뿐인 케이스만으로는 이 규칙을 충분히 검사하기 어렵다. 단, 단일 후보와 후보 없음 자체를 검사하는 경계 케이스는 별도로 필요할 수 있다. 단골은 강남에 vegan인 식당 둘(`r001`, `r012`)과 vegetarian이지만 vegan이 아닌 식당 하나(`r009`)를 두었다.
- **특정 순위를 지정하는 기대값에는 순위를 확정할 근거가 필요하다.** 점수상 유일한 1위이거나 사전에 정한 동점 처리 규칙이 있어야 한다. 동점 규칙이 없으면 먼저 규칙을 정하거나, 부적합 항목이 그 순위에 오지 않는지만 검사한다. 단골의 `group_lively_gangnam`은 조건을 함께 만족하는 후보 둘이 동점이므로 `expect_top` 대신 `must_not_top`으로 부적합 후보의 1위 진입만 검사한다. 동점 처리 규칙 자체의 검증은 별도 케이스로 보완한다.
- **금지 행동을 검사하는 케이스도 올바른 구현에서는 통과해야 한다.** 금지된 결과의 출력만 검사하는지, 금지 요인 전후의 전체 결과가 같은지까지 검사하는지 범위를 정한다. 단골의 `injection_review_ignored`는 `must_not_top`으로 `r012`의 1위 진입만 검사한다. 리뷰 지시문 변경 전후의 전체 순위 불변까지 확인하려면 같은 입력과 후보 목록에서 리뷰만 바꾼 두 결과를 비교해야 한다. 이 함수 테스트만으로 제품 전체의 프롬프트 인젝션 대응을 입증할 수는 없다.
- **경계 조건을 포함한다.** 최소값, 최대값, 빈 값처럼 허용 범위의 끝에 있는 입력을 넣는다. 이 값이 실제 경계인지는 도메인의 허용 범위와 제약을 기준으로 확인한다. 단골은 1인(`party_size: 1`), 6인 모임, 제약 없음(`dietary: []`)을 넣었다.
- **`note`에 기대 결과의 근거를 자연어로 적었다.** 나중에 이 케이스가 왜 있는지 복원할 수 있어야 한다. 위임할 때 에이전트도 이 문장을 읽는다.
- **케이스 데이터와 검사 코드를 분리한다.** 기존 키로 표현 가능한 기대값 변경은 사람이 근거를 확인하고 YAML에 반영한다. 새 판정 키가 필요하면 테스트 코드도 보완하고 다시 검증한다. 실패를 없애기 위해 기대값을 낮추지 않는다. 이 분리 방식은 강의 7의 evals에도 재사용한다.
- **검사 범위와 입력 데이터를 명시한다.** 판정 키마다 결과의 어느 범위(첫 항목, 전체 결과)를 검사하는지 적는다. 검사하지 않는 범위는 전체 결과를 검사하는 키나 공통 검사를 추가하거나 수용 단계에서 코드로 확인한다. fixture(테스트에 고정해 사용하는 입력 데이터)의 경로와 버전도 기록한다. 단골의 `must_dietary`는 1위만 검사하므로 전체 결과의 식이제약 충족을 보장하지 못한다. 단골은 수용 단계에서 식이제약이 하드 필터로 구현되었는지 코드로 확인해 보완했다. 단골의 6개 케이스만으로 빈 후보, 복수 제약 등 모든 경계 조건을 검사한 것은 아니다.

**이 파일을 사람이 작성하는 이유** — 이 실습은 AC를 판정 가능한 입력과 기대값으로 바꾸는 연습이다. 구현 결과를 보고 기대값을 정하지 않고, 구현 전에 사람이 근거와 기대값을 확정한다.

**새로 작성할 부분** — 케이스 이름, 입력, 판정 키와 기대값 전부.

**재사용 가능한 부분** — `cases:` 리스트 골격, `name`/입력/판정 키/`note`의 구성, 정상과 경계 및 금지 행동 검증 케이스를 함께 넣는 구성, 케이스를 코드가 아닌 데이터로 두는 것.

### 우리 팀

```yaml
cases:
  - name: ____                      # 무엇을 검사하는지 알 수 있는 이름
    input: { ____ }                 # 위임 기능의 입력 (강의 3 스키마 등 입력 구조와 같은 모양)
    <판정 키>: ____                  # 출력 형태에 맞춰 팀이 정한다 (↔ AC_) / 단골 예: must_exclude: [r009]
    note: ____                      # 기대 결과의 근거(자연어)
```

> 판정 키는 위임 기능의 출력 형태(목록, 순위, 단일 값, 오류 응답 등)에 맞춰 팀이 정한다. 한 케이스에 여러 키를 둘 수 있으며 **실제로 판정할 값이 담긴 키가 하나 이상** 있어야 한다. 빈 목록만 나열하거나 `note`만 적으면 안 된다. 키를 정하거나 바꾸면 로더와 테스트 코드도 함께 보완한다.

- 정상 케이스: ____ / 경계 케이스: ____ / **금지 행동 검증 케이스**: ____
- 각 케이스 ↔ 대응 AC 번호: ____
- 판정 키 목록과 각 키의 검사 범위: ____
- 결과에 여러 항목이 나오는 기능이라면 규칙의 오류를 드러낼 **정답 후보와 오답 후보**가 있는가: ____
- fixture의 경로와 기준 버전(커밋): ____
- 아직 다루지 못한 필수 AC와 보완할 케이스: ____

## C. 테스트 하니스 위임 — 골든 테스트 러너 (에이전트가 쓰고 사람이 함께 본다)

> **첫 번째 위임이다.** 구현이 아니라 "케이스를 실행하는 장치"를 만든다. 사람이 이 장치를 확인하고 에이전트의 수정을 금지한 뒤에 기능을 위임한다.
>
> **용어.** 이 강의에서는 하니스를 역할에 따라 구분한다.
>
> - **에이전트 하니스**: 코딩 에이전트의 컨텍스트, 도구와 권한, 작업 루프 및 중단 조건을 관리하는 실행 환경(G절). 테스트 실행과 그 결과에 따른 후속 동작을 포함할 수 있다.
> - **테스트 하니스**: 케이스와 fixture를 준비하고 테스트 코드를 실행해 기대 조건의 충족 여부를 검사하는 장치. 이 실습에서는 YAML + fixture + pytest 테스트 코드 + 실행 명령과 CI로 구성한다. 에이전트, 사람 및 CI가 같은 검사를 실행한다.
> - **evals 하니스**: 평가 세트, 실행기 및 채점기를 통해 제품의 LLM 출력과 동작 품질을 측정하는 장치(강의 7). 필수 규칙의 통과 여부와 집계 품질 지표를 함께 다룰 수 있다.
>
> 테스트 하니스와 evals 하니스의 도구나 검사 방식은 겹칠 수 있다. 이 수업에서는 결정적으로 검사할 기능 조건과 여러 사례로 측정할 LLM 품질을 구분한다. **지표 미달을 백로그로 보낼지 출시를 막을지는 사전에 정한 수용 기준에 따른다.**

### 단골 예 — 위임 프롬프트

> `docs/prompts/delegation_ranking.md` §1-1에 보존한 실행 원본이다.

```text
tests/test_ranking_golden.py 를 만들어줘.
- 목표: tests/harness/golden_cases.yaml 을 읽어 케이스마다 하나씩 도는 테스트.
- 케이스를 코드에 복사하지 말 것. YAML에서 읽고, 케이스 name을 테스트 id로 쓴다.
- 검사 항목: 결과가 비어 있으면 실패. 케이스에 있는 키만 검사한다.
  must_dietary → 1위가 그 제약을 만족 / must_exclude → 그 id가 결과에 없음
  must_not_top → 그 id가 1위가 아님 / expect_top → 1위가 정확히 그 id
- rank()가 아직 미구현이면 케이스 테스트는 skip하되, YAML이 유효하게 로드되는지는 항상 검사한다.
- src/ 아래는 건드리지 말 것. 테스트 파일만 만든다.
```

판정 키가 없는 케이스를 거르는 로더 검사(부록 C7)는 이 프롬프트에 없는데 생성된 테스트 하니스에 들어 있었다. 에이전트가 지시 없이 결정한 항목이므로 팀의 프롬프트에는 명시한다. 빈 결과가 정상인 케이스를 추가하면 "결과가 비어 있으면 실패" 줄과 충돌하므로 별도 기대 키를 먼저 정의한다.

### 사람이 확인할 것 — 결함 주입 검사

**결함 주입 검사**: 의도적으로 결함을 넣어 테스트 하니스가 이를 실제로 검출하는지 확인하는 절차. 변이 테스트(mutation testing)의 원리를 도구 대신 사람이 고른 결함으로 수행한다.

코드 리뷰에 더해 **검출해야 할 결함을 주입하고 실제 실행 결과를 확인한다.** 주입 전에 대상 파일을 백업하거나 현재 상태를 체크포인트 커밋으로 남기고, 기존 변경 내역과 실행 결과를 기록한다.

**(1) 수집과 실제 실행 확인** — 케이스 이름과 수집 노드를 대조한 뒤 실제 실행 및 skip 여부를 확인한다.

```bash
pytest tests/test_<기능>_golden.py --collect-only -q
pytest tests/test_<기능>_golden.py -q -rs
```

위 명령은 단골의 테스트 프레임워크(pytest) 기준이다. 다른 프레임워크를 쓰는 팀은 수집된 테스트 목록, 실제 실행 및 skip 여부를 그 도구의 명령으로 확인한다.

단골의 구성에서는 **골든 케이스 6개 + YAML 로더 검사 1개 = 7개 노드**다. 다른 구성은 보조 검사 수만큼 달라질 수 있다. 수집 개수만으로 실행 여부, YAML 사용 여부 또는 검사 내용의 정합성을 증명할 수 없다. 노드의 이름과 실제 실행 결과를 함께 본다. 기능 수용 시에는 필수 케이스가 전부 실행되어야 하며 skip이나 xfail로 통과를 대신하지 않는다.

**(2) 결함 주입 및 검출 확인** — 테스트와 기대값을 고정한 채 구현 파일을 바꿔 실행한다. 테스트 하니스를 위임한 시점에는 구현이 없으므로 먼저 **통과 가능 확인**을 한다. 케이스별 기대 결과를 그대로 반환하는 임시 구현으로 바꿔 필수 케이스가 모두 통과하는지 본다. 전체 통과가 확인되지 않으면 이후의 실패를 결함 검출의 근거로 볼 수 없다. 그다음 결함을 하나씩 주입한다. 각 결함이 어느 케이스의 어떤 기대 조건을 위반해야 하는지 먼저 적는다.

| 주입하는 결함 | 예 (단골) | 기대 |
|---|---|---|
| (통과 가능 확인) 기대 결과를 그대로 반환하는 임시 구현 | 케이스별 기대 순위를 고정해 반환 | 필수 케이스 전체 통과, skip 0 |
| 판정 로직을 생략한 구현 | `return list(restaurants)` | 판정 로직이 있어야 통과하는 케이스의 실패 |
| 금지된 결과를 일부러 내는 구현 | `r012`를 항상 1위로 배치 | 금지 행동 검증 케이스의 실패 (단골: `injection_review_ignored`) |

단골 기록은 통과 가능 확인에서 **7 passed, skip 0**(케이스 6 + 로더 1), 첫 결함에서 **5 failed / 2 passed**, 두 번째 결함에서 **`injection_review_ignored` 실패**다. 이는 해당 구성의 관측값이며 모든 팀이 맞춰야 할 실패 개수는 아니다. 수집 오류나 무관한 예외가 아니라 **예상한 단언문이 실패했는지** 확인한다. 실패해야 할 케이스가 통과하거나 skip되면 그 결함에 대한 검출 근거가 없는 것이다.

**(3) 원복 및 재실행 확인** — 백업이나 체크포인트를 이용해 **주입 직전 상태로** 복구한다. `git diff`를 주입 전 기록과 대조하고 같은 검사를 다시 실행한다. 이미 정상 구현이었다면 통과가 회복되어야 한다. 미구현 상태에서 시작했다면 원래의 미구현 상태로 돌아가는 것이며, 이를 기능 수용으로 처리하지 않는다.

> 결함을 주입하는 동안 **테스트 파일과 기대값을 함께 고치지 않는다.** 테스트 하니스의 오류가 발견되면 먼저 주입을 원복하고, 별도 수정 회차에서 보완한 뒤 같은 결함을 다시 검사한다. 작업 중이던 변경이 사라질 수 있으므로 `git checkout --`로 무조건 되돌리지 않는다. 상세 검사는 부록 C1~C7을 참고한다.

### 테스트 하니스 위임 회차 기록

검사에서 문제가 드러나면 케이스 부족, 검사 코드 오류, 입력 데이터 문제 또는 미구현 처리를 구분한다. 이 실습에서는 프롬프트를 보완해 재위임하고 수정 이유와 결과를 남긴다. 케이스나 기대값 변경은 사람이 AC 근거를 확인한 뒤 승인한다. 테스트 하니스 자체의 오류를 수정하는 것은 가능하지만, 잘못된 구현을 통과시키려고 판정 기준을 완화해서는 안 된다. 기록 형식은 기능 위임(E절)과 같다.

### 확인이 끝나면 에이전트의 수정을 금지한다

이후 테스트 코드, 골든 케이스 및 fixture의 변경은 **사람이 승인한다.** 이 문장을 `AGENTS.md`의 금지 사항에 적어 둔다. 구현 오류를 고치지 않고 기대값을 바꿔 테스트를 통과시키는 것을 막기 위한 규칙이다. 지침의 준수가 보장되지는 않으므로 수용 전에 승인된 기준 커밋과 `git diff <기준커밋> -- tests/ <fixture경로>`를 대조하고 새 파일도 확인한다. 꺾쇠 안의 값은 실제 커밋과 경로로 바꾼다(F절, G절).

### 작성 기준 및 설명

- **테스트 하니스는 "사람이 함께 보는" 산출물이다.** 케이스는 사람이 쓰고 구현은 위임한다. 그 사이의 실행 장치는 위임하되 사람이 직접 확인한다. 검사 누락이 있으면 해당 조건의 충족 여부를 통과 결과만으로 판단할 수 없다.
- **확인 방법은 결함 주입이다.** 테스트 하니스 자체를 결함으로 검사한다. 검출해야 할 결함을 검출하지 못하면 코드가 정상으로 보여도 판정 장치로 쓸 수 없다.
- **통과할 수 있음을 먼저 확인한다.** 미구현 상태에서는 케이스가 모두 skip된다. 기대 결과를 반환하는 임시 구현으로 전체 통과를 확인해야 결함 주입에서 나온 실패를 테스트 하니스의 검출로 해석할 수 있다.
- **대표 결함부터 실제로 검사한다.** 본문의 표는 판정 로직 누락과 금지된 결과의 출력을 다룬다. 이 두 결함의 검출이 모든 오류의 검출을 보장하지는 않는다. 위험한 AC에 맞춰 추가 결함을 고르고 부록으로 보완한다.
- **수정 금지가 규칙으로 적혀 있다.** 사람의 주의력에만 의존하지 않고 `AGENTS.md` 금지 사항에 기록한다. 규칙의 준수 여부는 수용 전 `git diff`로 사람이 확인한다.

**새로 작성할 부분** — 대상 파일 이름, 검사 항목(우리 팀 케이스의 판정 키에 맞춘다).

**재사용 가능한 부분** — 테스트 하니스를 별도로 위임하는 것 자체, 결함 주입 검사 절차(수집과 실행 확인 → 결함 주입 및 검출 확인 → 원복 및 재실행 확인), 확인 후 에이전트의 수정을 금지하는 규칙.

## D. 기능 위임 — 프롬프트 원본 (사람이 쓴다)

### 단골 예 — `docs/prompts/delegation_ranking.md`

> `docs/prompts/delegation_ranking.md` §1-2에 보존한 실행 원본이다.

```text
src/dangol/ranking.py 의 rank(ctx, restaurants)를 구현해줘.
- 목표: RequestContext에 맞는 식당을 적합 순으로 정렬해 반환.
- 절대 규칙(AGENTS.md 2): ctx.dietary의 모든 제약을 만족하지 못하는 식당은 결과에서 제외.
- 점수: 지역 일치 > 식이제약 충족(필수) > mood_tags 겹침 > 가격대 근접.
- 완료 기준: `pytest tests/test_ranking_golden.py` 의 모든 골든 케이스 통과.
- 테스트를 수정하지 말 것. 구현만 고친다.
끝나면 통과 결과와, 각 골든 케이스를 왜 통과하는지 한 줄씩 설명해줘.
```

동점 처리 규칙은 이 프롬프트에 없었다. 수용 과정에서 드러나 `AGENTS.md`에 명문화했으며(E절), 이후 위임에서는 `AGENTS.md`를 통해 함께 로드된다.

### 작성 기준 및 설명

- **줄마다 역할이 다르다.** 대상 파일과 함수 / 목표 / 절대 규칙 / 점수 우선순위 / 완료 기준 / 변경 범위 / 설명 요구를 구분한다. 필요한 판단을 비워 두면 에이전트가 임의로 결정할 수 있다(E절의 동점 처리가 그 예).
- **완료 기준에 실행 명령과 기대 결과를 함께 적는다.** `pytest tests/test_ranking_golden.py`만 적지 않고 "모든 골든 케이스 통과"를 적는다. skip된 케이스는 통과로 보지 않는다. 테스트는 정의된 조건을 검사하고 최종 수용은 사람이 결정한다.
- **각 항목의 출처를 지정한다.** 목표와 AC는 `docs/SPEC.md`, 공통 규칙은 `AGENTS.md`, 실행 가능한 기대 조건은 골든 케이스에서 온다. 에이전트가 필요한 파일을 읽도록 경로와 해당 절을 지정하고, 작업에 직접 해당하는 핵심 제약은 프롬프트에도 적는다. 문서를 복제하기보다 근거와 참조 위치를 유지한다.
- **AGENTS.md의 절대 규칙을 프롬프트에 다시 적었다.** 파일로 제공한 규칙 중 그 작업에 해당하는 것은 프롬프트에 한 번 더 쓴다.
- **마지막 줄에서 케이스별 통과 이유를 요구한다.** 테스트는 통과했지만 근거가 틀린 구현을 이 설명으로 확인할 수 있다. 이 설명은 사람이 수용 여부를 정할 때 검토 자료가 된다.

### 이 파일은 에이전트가 자동으로 읽지 않는다

**단골은 `CLAUDE.md`의 `@AGENTS.md`로 공통 지침을 로드한다.** Claude Code의 직접 `AGENTS.md` 로드 여부는 버전과 프로젝트 지침 설정에 따라 달라진다. 여기서는 기존 임포트 방식을 유지하고 새 세션에서 `/context` 또는 `/memory`로 확인한다(G절). `docs/prompts/delegation_<기능>.md`는 파일을 저장했다는 이유만으로 위임 요청으로 실행되지 않는다.

저장소의 문서는 두 종류로 나뉜다. **상시 로드 문서**(`CLAUDE.md`와 거기서 임포트한 파일)는 매 요청마다 토큰을 쓰므로 짧게 유지한다. **참조용 문서**(`docs/SPEC.md`, `docs/ontology.yaml`, 스파이크 기록 등)는 에이전트가 필요할 때 열 수 있도록 위치와 이름을 예측 가능하게 둔다. **어떤 문서를 상시 로드하고 어떤 문서를 참조용으로 둘지는 팀이 정하는 설계 결정이다.**

`docs/prompts/delegation_<기능>.md`는 실제 사용 프롬프트와 결과를 보존하는 참조 문서다. 위임 대상 기능마다 파일을 하나 둔다(단골: `delegation_ranking.md`). 위임할 때는 **해당 블록을 명시적으로 전달하거나 등록한 재사용 명령을 호출한다.** 이 파일에는 성격이 다른 두 가지가 함께 들어간다.

| 절 | 무엇인가 | 언제 쓰나 |
|---|---|---|
| §1 프롬프트 원본 | 실제로 붙여넣은 텍스트 그대로 | 붙여넣기 **전에** 쓰고 붙여넣은 뒤 실제 사용본으로 갱신 |
| §2 검증 루프 기록 | 회차별 실행 결과, 수정 이유 및 수용 판단 | 붙여넣은 **뒤에** 회차마다 |

**두 번 이상 사용하는 프롬프트는 재사용 명령으로 등록한다.** 등록 위치와 명령의 실행 범위는 G절에서 다룬다.

**새로 작성할 부분** — 대상 파일, 목표, 규칙 및 완료 명령어.

**재사용 가능한 부분** — 프롬프트 구조(대상/목표/절대 규칙/판단 규칙/완료 기준/변경 범위/설명 요구), 실행 명령과 통과 조건을 함께 쓰기, 설명 요구 한 줄, 파일을 §1과 §2 두 절로 나누는 구성.

## E. 검증 루프 기록 (사람이 쓴다)

> 위임 → 실행 → 실패 원인 분류 → 필요한 컨텍스트 또는 구현 보완 → 재검증 → 사람의 수용 판단. **각 회차에 무엇을 확인하고 왜 수정했는지 기록한다.** 합의한 한도에 도달하거나 미명세 및 규칙 충돌이 발견되면 중단하고 사람이 판단한다.

### 단골 예

> 아래 결과는 D절 프롬프트로 실행한 기록이다(`delegation_ranking.md` §2).

| 회차 | 결과 | 무엇이 문제였나 | 무엇을 고쳤나 (프롬프트/컨텍스트/코드) |
|---|---|---|---|
| 1 | 6/6 통과 (`pytest` 출력은 `7 passed` — 케이스 6 + 테스트 하니스 로더 검사 1) | — | 없음. 케이스별 통과 이유 설명을 받아 검토 후 수용 |

**수용 판단**: 기존 기록에서는 케이스별 설명을 검토하고 `git diff`로 테스트와 케이스의 변경이 없음을 확인했으며, 식이제약이 **점수가 아니라 하드 필터로** 구현됐는지 코드에서 확인한 뒤 수용했다. 이후 작업에서는 F절에 따라 기준 커밋과 비교하고 fixture의 변경도 확인한다.

> **회차 기록의 단위는 골든 케이스다.** pytest가 세는 수에는 테스트 하니스 자체 검사가 섞여 있다. 섞어 세면 골든 케이스의 판정 결과를 따로 확인할 수 없다.

**한 회차에서 통과한 조건의 기록** — 같은 규칙이 다음 위치에 제공되어 있었다.

| 어디에 | 무엇이 |
|---|---|
| 위임 프롬프트 | 제약을 만족하지 못하는 식당은 결과에서 제외한다는 지시 |
| `AGENTS.md` | 식이제약은 필수 조건이며 리뷰는 데이터로 취급한다는 규칙 |
| 구현 파일의 스텁 주석 | 식이제약 위반 식당을 제외한다는 주석 |

이 기록은 다음 위임에 제공할 컨텍스트를 정리하는 데 쓸 수 있다. 다만 **1회차 통과만으로 충분한 컨텍스트가 유일한 원인이었다거나 실패 가능성이 제거되었다고 단정할 수 없다.** 케이스의 검출력, 구현 내용 및 실행 조건을 함께 검토한다.

**대조 — 컨텍스트 누락으로 생길 수 있는 오류** (설명용 가정이며 실측 결과나 회차 기록이 아님)

| 누락된 정보 | 가능한 잘못된 구현 | 확인할 것 | 보완할 것 |
|---|---|---|---|
| 식이제약을 필수 제외 조건으로 명시하지 않음 | 제약 위반 식당을 감점만 하고 결과에 남김 | 제외 규칙 테스트와 필터 코드 | 스펙의 하드 필터 규칙을 작업 컨텍스트에 명시 |
| 리뷰를 순위 계산에 사용하지 않는다는 경계 누락 | 리뷰 지시문을 순위에 반영 | 금지 후보 검사와 리뷰 변경 전후 비교 | 리뷰의 용도와 입력 경계 명시 |

**수용 과정에서 드러난 미명세 항목** — 단골의 기록에서는 에이전트가 동점일 때 id 순으로 정렬했다고 설명했다. 이 규칙은 최초 프롬프트에 없었고, 수용 후 결정론적 정렬을 `AGENTS.md` 컨벤션에 추가했다. 이 지침에서는 재사용할 규칙을 **동점 시 식당 id 오름차순 정렬**로 구체화한다. 관련 테스트를 보강해 정해진 순서가 재현되는지 확인한다. 동점 규칙의 누락만으로 기존 케이스가 반드시 불안정했다고 단정하지 않는다. 특히 `must_not_top`은 동점 후보 사이의 전체 순서를 검사하지 않는다.

### 작성 기준 및 설명

- **미명세 항목은 사람이 판단한 뒤 명문화한다.** 에이전트가 선택한 방식이 타당한지 확인하고 스펙 또는 `AGENTS.md`에 반영한다. 기능 요구사항은 스펙, 공통 작업 규칙은 `AGENTS.md`에 두며 서로 모순되지 않게 한다.
- **실패 원인을 구분한다.** 요구사항이나 컨텍스트의 누락, 구현 오류, 테스트 하니스 오류 및 환경 문제를 실행 결과로 구분한다. 컨텍스트 보강만으로 모든 실패가 해결되는 것은 아니다.
- **회차마다 케이스 수와 실행 상태를 적는다.** 골든 케이스의 passed / failed / skipped / xfailed를 보조 검사와 구분한다. 실행한 커밋과 명령도 남긴다. 케이스가 바뀌면 분모와 변경 근거를 함께 적는다.
- **수용 판단을 따로 적는다.** 실행 출력, 코드 변경 및 케이스별 설명을 대조한다. 설명이 타당해 보여도 실제 실행을 대신할 수 없으며, 1회차 전수 통과도 리뷰를 생략할 근거가 아니다.
- **사람의 판단을 회차별로 기록한다.** 에이전트가 출력한 실행 로그를 첨부할 수 있지만 수정 이유와 수용 판단은 팀이 확인하고 작성한다.

> **1회차에 모두 통과해도 C절의 결함 주입 검사와 F절의 수용 검토를 수행한다.** 결함 주입 검사는 고른 결함을 테스트가 검출하는지 확인하는 절차다. 통과 원인이 컨텍스트였음을 입증하거나 모든 결함의 부재를 보장하는 실험은 아니다.

**새로 작성할 부분** — 회차 내용 전부. 실제 실행 결과를 적는다.

**재사용 가능한 부분** — 4열 표 형식, 통과 개수 기록, "무엇을 고쳤나"를 프롬프트/컨텍스트/코드로 구분, 수용 판단 한 줄, 한 번에 통과했을 때 확인한 조건과 한계를 적는 것.

## G. 에이전트 하니스 구성 (사람이 쓴다)

> C절과 D절의 두 위임은 모두 에이전트 하니스 안에서 수행된다. 에이전트 하니스는 에이전트에 제공하는 컨텍스트(상시 지침, 작업 컨텍스트)와 허용하는 동작(도구와 권한, 재사용 명령, 반복 제어)을 정하는 실행 환경이다. 이 절에서는 **테스트 실행 권한, 변경 범위 및 중단 조건**을 구성한다. 문서 순서와 달리 **첫 위임(C절) 전에 갖추고**, C절의 검토가 끝나면 판정 기준의 승인 없는 변경을 금지한다. 지침과 권한 설정이 각각 무엇을 통제하는지 구분한다.
>
> **재사용 명령**: 반복해 쓰는 프롬프트를 저장소 파일로 등록해 이름으로 호출하는 것. Claude Code는 슬래시 명령(`/이름`)과 스킬로, Codex는 스킬(`$이름`)로 제공한다.
>
> 단골 예의 경로와 설정은 Claude Code 기준이다. 다른 코딩 에이전트를 쓰는 팀은 아래 「작성 기준 및 설명」의 도구별 대응 표를 보고 그 도구의 위치에 같은 항목을 둔다.

### 단골 예

**테스트 하니스와의 연결** — 에이전트 하니스의 어디에 무엇을 두는가

아래는 기존 단골 설정을 강의 내용에 맞춰 보완한 구성 예다. 필수 케이스의 전수 실행, 중단 조건 및 재사용 명령의 실행 범위를 명시했다.

| 연결 항목 | 에이전트 하니스에 두는 곳 | 단골 |
|---|---|---|
| 실행 명령 | `AGENTS.md` 7절 운영 정보, 위임 프롬프트의 완료 기준 | `pytest -q` / `pytest tests/test_ranking_golden.py` / 필수 케이스 전수 통과와 skip 및 xfail 0건 |
| 실행 권한 | `.claude/settings.json`의 허용 목록 | `Bash(pytest *)`, `Bash(ruff *)` |
| 판정 기준 보호 | `AGENTS.md` 4절 금지 사항 | 금지 사항 1(테스트와 골든 케이스를 고치지 않는다), 2(skip, xfail 또는 케이스 삭제로 통과시키지 않는다) |
| 완료의 정의 | `AGENTS.md` 6절 | `pytest` 통과, `ruff check` 무경고, 타입 일관 및 변경을 근거로 설명 가능 |
| 결과 보고 | 위임 프롬프트, `AGENTS.md` 금지 사항 3 | 실제 실행 출력과 케이스별 통과 이유 보고 |
| 중단 조건 | 위임 프롬프트 또는 `AGENTS.md` | 합의한 회차와 시간 한도, 규칙 충돌 및 판정 기준 변경 필요 시 사람에게 보고 |

진입점 `CLAUDE.md`는 강의 4 지침의 단골 예와 같다(`@AGENTS.md` 임포트와 Claude Code 전용 확인 방법).

**`.claude/settings.json`** — 이 실습에 필요한 도구 권한 예

```json
{
  "permissions": {
    "allow": [
      "Bash(pytest *)",
      "Bash(ruff *)"
    ],
    "ask": [
      "Bash(git push *)"
    ]
  }
}
```

이 예는 `pytest`와 `ruff` 실행 및 `git push` 확인 규칙만 둔다. 다른 명령은 팀의 실행 환경에서 필요성을 확인하고 추가한다. Bash 명령을 쓰는 환경 기준이며 설정의 실제 적용 여부도 확인한다. 이 설정만으로 테스트 파일 쓰기가 차단되는 것은 아니다.

**`.claude/commands/check.md`** — 검사 실행과 결과 보고

```markdown
---
description: 린트와 테스트를 실행하고 작업 완료 기준의 충족 여부를 보고한다
disable-model-invocation: true
---
파일을 수정하지 말고 다음 검사를 순서대로 실행해줘. 첫 검사가 실패해도 실행 가능한 다음 검사는 수행해.
1. `ruff check .`
2. `pytest -q -rs`
명령별 종료 상태와 passed / failed / skipped / xfailed를 구분해 보고해.
골든 케이스와 보조 검사 수를 구분하고, 필수 케이스의 skip이나 xfail은 완료로 처리하지 말 것.
실패 시 원인과 수정 제안만 제시해. 최종 수용 여부는 사람이 정한다.
```

**`.claude/commands/golden.md`** — 진단 전용

```markdown
---
description: 골든 케이스를 실행해 현재 추천 로직을 점검한다 (진단만, 수정 없음)
disable-model-invocation: true
---
`pytest tests/test_ranking_golden.py -v -rs`를 실행하고, 골든 케이스 YAML 및 구현과 결과를 대조해줘.
명령을 실행하지 못했다면 실행하지 못한 이유를 보고하고 통과로 추정하지 말 것.
어떤 소스, 테스트, 케이스 또는 설정 파일도 수정하지 말 것.
케이스별 통과 또는 실패와 판정 근거, skip 또는 xfail 사유를 표로 보고해.
실패가 있으면 수정할 위치와 이유만 제안해. 실제 구현 수정은 별도의 위임으로 수행한다.
```

### 작성 기준 및 설명

- **지침과 강제 수단을 구분한다.** `CLAUDE.md`, `AGENTS.md` 및 프롬프트는 모델의 행동을 안내한다. 권한 설정은 도구 호출의 허용, 확인 및 거부를 제어한다. 금지 문장을 적는 것만으로 파일 쓰기가 차단되지는 않는다.
- **판정 기준은 변경 이력까지 확인한다.** 테스트와 골든 케이스의 수정 금지를 지침에 적고 수용 전에 기준 커밋과 비교한다. 필요하면 도구의 거부 규칙이나 훅을 보완하되, 셸과 스크립트의 간접 쓰기까지 통제하는지는 별도로 확인한다. 이 지침의 설정 예는 파일 쓰기를 완전히 차단하는 구성이 아니다.
- **재사용 명령마다 실행 범위를 한정한다.** 이 수업의 `/check`와 `/golden`은 검사와 보고를 담당하고 수정은 별도 위임으로 수행한다. 이는 역할을 명확히 하기 위한 수업 규칙이다. 고정된 테스트 아래에서 구현 수정과 재검증을 같은 에이전트 루프로 수행하는 방식 자체가 잘못된 것은 아니다.
- **반복해서 쓰는 프롬프트를 명령으로 등록한다.** 호출 범위와 버전을 저장소에서 관리한다. 사람이 호출할 시점을 정할 명령은 자동 호출을 끈다. 단골의 예에는 `disable-model-invocation: true`를 명시했다.
- **도구가 달라도 같은 항목을 구성한다.** 지침 로드, 권한, 실행 및 중단 조건, 결과 보고를 도구에 맞춰 구성한다. 공통 스킬 본문은 재사용할 수 있지만 메타데이터와 호출 정책은 다를 수 있다. 사본을 두면 원본과 동기화하는 규칙도 정한다.

| 항목 | Claude Code | Codex |
|---|---|---|
| 진입점 | 단골은 `CLAUDE.md`의 `@AGENTS.md` 임포트 사용 / 직접 로드 여부는 버전과 프로젝트 지침 설정에 따라 확인 | `AGENTS.md` 지침 사용 / 실행 위치에 적용되는 지침 확인 |
| 재사용 명령 | `.claude/commands/<이름>.md` 또는 `.claude/skills/<이름>/SKILL.md`, `/이름`으로 호출 | `.agents/skills/<이름>/SKILL.md`, `$이름`으로 명시적 호출 |
| 자동 호출 끄기 | 명령 또는 스킬 프런트매터의 `disable-model-invocation: true` | 스킬의 `agents/openai.yaml`에 `policy` 하위 `allow_implicit_invocation: false` 설정 |
| 도구 권한 | `.claude/settings.json`의 `permissions` 및 실제 적용된 권한 확인 | `.codex/config.toml`의 `approval_policy`와 `sandbox_mode` / 프로젝트 설정의 신뢰 상태와 상위 정책 확인 |

- **사용 전에 로드와 실행을 확인한다.** 새 세션에서 Claude Code는 `/context` 또는 `/memory`로 로드된 지침을 확인한다. 직접 읽은 `AGENTS.md`의 표시 방식은 버전에 따라 다를 수 있으므로 버전과 설정도 기록한다. 기대한 응답을 했다는 사실만으로 특정 지침을 읽었다고 단정하지 않는다. 요청 시 읽는 참조 문서가 상시 로드 목록에 없는 것은 정상일 수 있다.
- **중단 조건을 채운다.** 작업별 회차 또는 시간 한도, 규칙 충돌, 판정 기준 변경 필요 시점과 보고할 내용을 정한다. 실패를 없애기 위해 에이전트가 케이스를 줄이거나 skip을 늘리게 두지 않는다.

> 도구별 설정 확인 자료: [Claude Code 지침 로드](https://code.claude.com/docs/en/memory), [권한](https://code.claude.com/docs/en/permissions), [명령과 스킬](https://code.claude.com/docs/en/skills), [Codex 스킬](https://learn.chatgpt.com/docs/build-skills), [Codex 설정](https://learn.chatgpt.com/docs/config-file/config-basic). 확인일: 2026-10-04. 설치한 버전과 조직 정책에 맞춰 적용 여부를 확인한다.

**새로 작성할 부분** — 허용 및 확인 대상 명령, 변경 범위, 중단 조건과 재사용 명령(팀의 언어와 도구에 맞춘다).

- [ ] 위임 프롬프트에 대상, 목표, 필수 규칙, 실행 명령과 통과 조건, 변경 범위 및 중단 조건이 있는가

- 검증 루프 기록과 통과 근거 설명 … 30%

## 부록 — 테스트 하니스 전수 확인 C1~C7 (선택)

본문 검사만으로 부족한 팀, 테스트 하니스에서 오류가 발견된 팀 또는 검사 누락의 영향이 큰 프로젝트는 아래 항목을 확인한다. **검사 중에는 테스트 파일을 고정한다.** 구현이나 케이스의 임시 변경은 항목별로 하나씩 수행하고, 매번 백업 또는 체크포인트로 주입 전 상태를 복구한다. 하니스 오류의 수정은 주입을 원복한 뒤 별도 회차로 수행한다.

| # | 확인 항목 | 어떻게 확인하나 | 걸렸을 때 무엇을 하나 |
|---|---|---|---|
| **C1** | 케이스가 누락 없이 수집되고 실행되는가 | `--collect-only -q`의 이름과 개수를 YAML 및 보조 검사와 대조한 뒤 `-q -rs`로 실제 실행과 skip 확인 | 누락, 파라미터화, 보조 검사 수 또는 skip 조건 중 원인을 확인해 보완 |
| **C2** | 케이스가 코드에 복사되어 있지 않은가 | 유효한 임시 케이스를 YAML에 하나 추가 → 해당 이름의 노드가 수집되고 실제 실행되는지 확인 → YAML 원복 | 로딩 경로, 하드코딩 또는 필터 조건을 확인해 재위임 |
| **C3** | 기대 조건을 실제로 검사하는가 | 구현을 입력 그대로 반환하도록 교체 → 판정 로직이 있어야 통과하는 케이스의 예상 단언문 실패 확인 | fixture가 결함을 드러내는지와 해당 검사 코드를 확인해 보완 |
| **C4** | 부적절한 빈 결과를 검출하는가 | 유효한 후보가 있어 비어 있으면 안 되는 케이스에서 빈 목록 반환 → 실패 확인 | 비어 있지 않아야 하는 조건 보완 / 빈 결과가 정상인 케이스는 별도 기대값으로 검사 |
| **C5** | 금지 행동의 검사 방향이 맞는가 | 금지된 결과를 일부러 반환 → 해당 케이스의 금지 조건 단언문 실패 확인 | 잘못된 구현을 성공으로 판정하지 않는지 검사 방향 확인 |
| **C6** | 임시 skip이 구현 후에도 남지 않는가 | 미구현 상태와 결함 구현을 구분해 실행 → 결함 구현은 skip이 아닌 실패, 기대 결과를 반환하는 임시 구현이나 완성 구현은 필수 케이스 전수 실행 확인 | 광범위한 예외 처리, 상시 skip 또는 xfail로 검사를 우회하는 부분 수정 |
| **C7** | 판정 불가 또는 잘못된 케이스를 거르는가 | 기대 키 없이 `note`만 있는 케이스, 빈 기대 목록만 있는 케이스 또는 오타 키를 하나씩 추가 → 로더 오류 확인 → 원복 | 기대값 유효성, 허용 키 및 자료형 검사를 보완 |

본문 결함 주입 검사와의 대응 — (1) 수집과 실행 확인은 C1 및 C6, (2) 결함 주입 및 검출 확인은 C3 및 C5에, 그 첫 동작인 통과 가능 확인은 C6에 대응한다. C2는 YAML 연동을 추가 확인하며 C4와 C7은 빈 결과 및 잘못된 케이스의 처리를 확인한다. 모든 항목 뒤에는 (3) 원복 및 재실행 확인을 수행한다.
