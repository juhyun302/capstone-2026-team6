# [강의 6] 아키텍처, RAG, 도구 — 산출물 작성 지침

> 공통 예제 **단골**(AI 맛집 추천과 예약 비서)이 이 산출물을 실제로 어떻게 만들었는지 확인하고, 같은 항목에 우리 팀의 산출물을 작성한다.
> 스펙(강의 4)이 **무엇을 만들지**를 정했다면, 이 강의의 산출물은 **어떻게 조립할지**를 정한다.

## 이번 강의에서 만드는 것

| # | 산출물 | 형식 | 작성자 | 무엇을 담는가 | 저장소 위치 | 선행 산출물 | 이후 어디에 쓰이나 |
|---|---|---|---|---|---|---|---|
| 1 | 아키텍처 설계서 | Markdown | 사람 | 데이터 흐름, 구성 요소, 도구 목록, 오케스트레이션 방식, 실패 처리, 가드레일 | `docs/ARCHITECTURE.md` | 강의 4 스펙, 강의 3 스키마, 강의 5 골든 케이스 | 강의 7 evals의 측정 대상 정의 / 검증 및 테스트 강의 / LLMOps 강의 |
| 2 | RAG 설정 | YAML | 사람 | 대상 문서, 청킹, 임베딩, 저장소, 검색 파라미터, 강제 규칙 | `config/rag.yaml` | 1의 RAG 절 | 강의 7 근거 인용률 측정 / LLMOps 강의의 실험 파라미터 |
| 3 | 도구 정의 | 1의 표 + 코드 | 사람(표) / 에이전트가 쓰고 사람이 검증한다(코드) | 시그니처(도구 이름, 입력 인자와 타입, 반환 타입), 모델이 언제 쓸지 판단할 설명, 부작용 | `src/<패키지>/tools/` | 강의 3 스키마 | 오케스트레이션의 실행 단위 |

> **작성자** — 아키텍처 설계서(`docs/ARCHITECTURE.md`)와 RAG 설정(`config/rag.yaml`)은 사람이 쓴다. 무엇을 조립하고 무엇을 안 쓸지, 파라미터 값을 왜 그렇게 두는지는 제품의 판단이라 에이전트에게 맡기면 근거를 잃는다. 도구는 표(시그니처, 설명, 부작용)를 사람이 정하고, 그 표대로 코드를 만드는 일은 에이전트에게 맡기되 사람이 검증한다 — 강의 5의 기능 위임과 같은 방식이다.
>
> 파일 이름은 팀 규칙에 맞게 바꿔도 되지만 **저장 위치는 맞춘다** — 리뷰 때 이 경로를 본다. 저장소 전체 구조는 `00_README.md`의 "저장소 표준 구조"를 본다.
>
> RAG를 쓰지 않는 제품이라면 2는 만들지 않는다. 대신 1의 해당 절에 **"왜 검색이 필요 없는가"**를 적는다 — 안 쓰는 결정도 설계다.

## 이 지침 읽는 법

| 구분 | 뜻 |
|---|---|
| **단골 예시** | 제출 가능한 수준으로 채워진 예. |
| **작성 기준 및 설명** | 작성 내용에 대한 판단 근거. |
| **새로 작성할 부분** | 도메인에 따라 내용이 달라지는 항목. 단골 예시를 그대로 옮기면 인정하지 않는다. |
| **재사용 가능한 부분** | 형식과 규약. 그대로 사용할 것을 권장한다. |
| **우리 팀** | 팀이 작성하는 항목. |

**복제에 대하여** — 문서 절 구성과 YAML 키는 그대로 써도 된다. **구성 요소, 도구, 파라미터 값은 우리 제품의 스펙과 AC에서 나와야 한다.** 특히 "왜 이 구조인가"에 답하지 못하면 그 항목은 인정하지 않는다.

## A. 데이터 흐름과 구성 요소

### 단골 예시 — `docs/ARCHITECTURE.md` 1~2절

**1. 한눈에 보는 데이터 흐름**
사용자 발화 → 파싱(RequestContext) → 리뷰 RAG 검색 → 랭킹(강의 5 함수) → 근거 정리와 추천 → (선택)예약(mock)

**2. 구성 요소**

- `parser.py` — 자연어 → RequestContext (강의 3 산출물)
- `retrieval.py` — 리뷰 벡터 검색(RAG). **이번 강의 구현 대상**
- `ranking.py` — 제약 하드필터 + 스코어 (강의 5 산출물)
- `reservation.py` — `make_reservation`(mock). **이번 강의 도구화**
- 오케스트레이션 — workflow(처리 순서를 코드가 고정, 별도 프레임워크 없이 함수 조합). 모델 호출은 파싱 1회

### 작성 기준 및 설명

- **흐름이 한 줄이다.** 화살표로 이은 한 문장으로 제품 전체가 표현된다. 이 한 줄을 못 쓰면 아직 아키텍처가 없는 것이다. 그림보다 이 문장이 먼저다.
- **구성 요소마다 어느 강의의 산출물인지 표시했다.** parser는 강의 3, ranking은 강의 5. 이미 만든 것과 이번 강의에서 만들 것이 구분되어 있어 작업 범위가 자동으로 정해진다.
- **오케스트레이션을 "프레임워크 없이 함수 조합"으로 명시했다.** 무엇을 안 쓰는지 적는 것도 설계다. 프레임워크를 도입하면 그 결정과 이유를 여기에 적는다.
- **파일 단위로 쪼갰다.** 개념 단위("검색 모듈")가 아니라 실제 파일명이라 그대로 저장소 구조가 된다.

**새로 작성할 부분** — 흐름과 구성 요소 전부.

**재사용 가능한 부분** — 흐름을 화살표 한 줄로 먼저 쓰기, 구성 요소를 실제 파일명으로 쓰고 출처 강의를 병기하기, 이번 강의 작업 대상 표시.

## B. 도구 목록 (function calling)

### 도구 코드 생성 절차

도구 코드(`src/<패키지>/tools/`)는 모델의 도구 호출 요청을 받아 이미 있는 함수를 실행하는 연결 함수다. 새 기능을 만드는 것이 아니라, 기존 함수를 모델이 호출할 수 있는 형태로 연결한다. 도구 코드 하나가 하는 일은 다음과 같다.

1. 모델의 도구 호출 요청(도구 이름과 JSON 인자)을 받는다.
2. 인자를 검증하고 기존 함수가 받는 타입으로 바꾼다(단골은 JSON → `RequestContext`).
3. 기존 함수를 호출한다.
4. 결과를 모델에게 돌려줄 형식(도구 실행 결과)으로 바꿔 반환한다.

도구 코드는 연결할 함수가 모두 구현된 뒤, 아키텍처 설계서(`docs/ARCHITECTURE.md`) 3절의 도구 표를 기준으로 만든다. 표와 판정 기준은 사람이 정하고, 코드는 에이전트에게 위임한 뒤 사람이 검증한다. 강의 5의 위임 순서(판정 기준을 먼저 확정하고 구현은 나중에)와 같다.

| 단계 | 작성자 | 할 일 | 결과물 |
|---|---|---|---|
| 1. 도구 표 확정 | 사람 | 도구마다 이름, 시그니처, 설명, 부작용을 정한다. 시그니처의 타입은 온톨로지 클래스 이름을 쓴다 | `docs/ARCHITECTURE.md` 3절 표 |
| 2. 연결할 기존 함수 지정 | 사람 | 도구마다 어떤 기존 함수나 외부 API를 호출할지 정한다 | `docs/ARCHITECTURE.md` 3절 표 아래 대응 목록 |
| 3. 사용자 승인 위치 결정 | 사람 | 쓰기 도구 실행 전에 무엇을 보여 주고 승인받을지(실행할 도구와 인자) 정한다. 승인을 흐름이 쓰기 도구 앞에서 멈추고 받는 구조인지, 도구가 승인 값을 인자로 요구하는 구조인지 정한다 | `docs/ARCHITECTURE.md` 3절(승인 대상), 5절(승인 위치) |
| 4. 도구 계약 테스트 | 사람(조건) / 에이전트가 쓰고 사람이 함께 본다(테스트 코드) | 도구 코드가 지켜야 할 조건을 테스트로 고정한다. 강의 5의 골든 케이스 테스트와 함께 테스트 하니스의 일부이며, 같은 방식(결함 주입 검사 후 에이전트 수정 금지)으로 확인한다. 기존 함수의 정확성이 아니라 연결 함수의 계약을 검사한다. 아래 계약 조건 참고 | `tests/test_tools.py` |
| 5. 도구 코드 위임 | 에이전트가 쓰고 사람이 검증한다 | 4의 테스트를 확정한 뒤 코딩 에이전트에게 위임한다. 1의 표에 맞춰 인자를 받고 2의 함수를 호출하는 코드를 만든다. 도구 정의의 설명 항목에는 표의 설명 문장을 그대로 쓴다(단골은 함수 docstring에 두고 도구 정의로 전달). 테스트는 고치지 않는다 | `src/<패키지>/tools/` |
| 6. 수용 | 사람 | 계약 테스트 통과, `git diff`로 테스트 미변경, 표와 코드의 시그니처와 설명 일치를 확인한다 | 커밋 |

**계약 조건** — 4단계의 테스트가 검사할 내용이다. 골든 케이스는 판정 기준을 YAML 데이터로 따로 두지만, 도구 계약은 조건이 적어 테스트 코드 안에 단언문으로 둔다.

- 시그니처의 타입이 온톨로지 클래스(단골은 `RequestContext`, `Restaurant`, `Reservation`)인가
- 읽기 도구가 데이터의 상태를 바꾸지 않는가
- 쓰기 도구가 사용자 승인 없이, 또는 승인과 다른 인자로 호출되면 실행되지 않는가
- 쓰기 도구가 실행되면 상태가 확정 값으로 바뀌는가(단골은 `Reservation.status`가 `confirmed`)

**단골의 경우** — 도구 세 개 모두 이미 있는 함수를 호출한다(아래 단골 예시의 "연결되는 기존 기능"). 연결되는 함수는 각자의 테스트로 이미 검증한다. `ranking.py`는 강의 5의 골든 케이스, `retrieval.py`는 이번 강의의 검색 케이스로 판정하고, `reservation.py`는 스캐폴드의 mock이다. 그래서 도구 계약 테스트는 랭킹 순서나 검색 품질을 다시 보지 않는다. 도구 코드는 리뷰 검색을 구현한 다음 이 절차로 만든다.

`tests/test_tools.py`와 pytest 명령은 단골(Python, pytest) 기준이며 팀의 언어와 테스트 프레임워크를 따른다.

### 단골 예시 — 3절

| 도구 | 시그니처 | 설명(모델이 언제 쓸지 판단할 문장) | 부작용 |
|---|---|---|---|
| search_restaurants | `(context: RequestContext) -> [Restaurant]` | 조건에 맞는 후보 식당을 찾는다 | 없음(읽기) |
| get_reviews | `(restaurant_id) -> [ReviewChunk]` | 추천 근거가 될 리뷰 청크를 가져온다 | 없음(읽기) |
| make_reservation | `(restaurant_id, time_slot, party_size) -> Reservation` | 예약을 잡는다(mock) | 있음(쓰기, 실행 전 사용자 승인) |

원칙: 도구는 적게, 스키마는 좁게(타입, 필수, 허용값), 쓰기 도구는 실행 전 사용자 승인.

`ReviewChunk`는 Review를 검색 단위로 나눈 청크다(RAG 색인용 파생 타입, 온톨로지 클래스 아님).

연결되는 기존 기능: search_restaurants → `ranking.py`의 하드필터 후보 / get_reviews → `retrieval.py`의 리뷰 검색 / make_reservation → `reservation.py`의 `make_reservation`(mock).

사용자 승인: 실행할 식당, 시간대, 인원을 사용자에게 보여 주고 승인받은 인자 그대로 실행한다. 인자가 바뀌면 다시 승인받는다.

### 작성 기준 및 설명

- **도구를 최소로 두었다.** 도구가 늘수록 모델은 무엇을 언제 쓸지 혼동한다. "있으면 좋을 것 같은" 도구를 넣지 않는다 — 강의 3에서 필드를 줄인 것과 같은 논리다.
- **시그니처의 타입이 온톨로지 클래스 이름 그대로다.** `RequestContext`, `Restaurant`, `Reservation`. 강의 2에서 정한 어휘가 함수 시그니처까지 그대로 온다. 여기서 새 이름이 나타나면 어휘가 깨진 것이다. `ReviewChunk`는 새 도메인 개념이 아니라 Review를 검색 단위로 나눈 파생 타입이라 아키텍처 설계서에 그렇게 밝혀 두었다.
- **설명 열이 "모델이 언제 쓸지 판단할 문장"이다.** 사람용 주석이 아니다. 모델이 읽는 선택 기준이다. "식당 검색 함수"가 아니라 "조건에 맞는 후보 식당을 찾는다"라고 쓴 이유다.
- **부작용 열이 따로 있다.** 읽기 도구와 쓰기 도구를 구분해야 "쓰기는 실행 전 사용자 승인"이라는 규칙을 걸 수 있다. 예약, 결제, 발송처럼 되돌릴 수 없는 도구는 실행할 도구와 인자를 사용자에게 보여 주고 승인받은 뒤 그 인자 그대로 실행한다.
- **도구 코드는 이 표에서 만든다.** 표가 계약 테스트와 도구 정의 설명의 원천이다. 코드에서 시그니처나 설명을 바꾸면 표부터 고친다.

**새로 작성할 부분** — 도구 목록 전부.

**재사용 가능한 부분** — 4열 표(도구/시그니처/설명/부작용), 타입을 온톨로지 클래스명으로 쓰기, 설명을 모델용 판단 문장으로 쓰기, "적게, 좁게, 쓰기는 사용자 승인" 원칙, 도구 코드 생성 절차와 계약 조건.

|---|---|---|---|

## C. RAG 설계

### 단골 예시 — 4절 요약

- 대상 문서: 식당별 리뷰 텍스트
- 청킹: 리뷰 1건 = 1청크(리뷰가 짧음), 긴 리뷰는 문장 분리
- 임베딩과 저장소: 경량(sqlite-vec/chroma), top_k=4, 코사인 유사도
- 인용: 추천 이유에 최소 1개 리뷰 근거를 포함(AC2)
- 하드 제약: 식이제약은 "검색"이 아니라 "필터"로 강제(AC1)

**상세 — `config/rag.yaml`**

```yaml
source:
  documents: reviews            # 대상: 리뷰 텍스트
  fields: [text]
  metadata: [restaurant_id, rating, author, date]

chunking:
  strategy: per_review          # 리뷰 1건 = 1청크(리뷰가 짧음)
  fallback: by_sentence         # 긴 리뷰는 문장 단위로 분리
  max_chars: 500

embedding:
  provider: local               # 추상화: local | openai | anthropic
  model: text-embedding-3-small # 예시(교체 가능)
  dim: 1536

store:
  backend: sqlite               # 소규모: sqlite-vec | chroma
  path: data/index/reviews.db
  metric: cosine

retrieval:
  top_k: 4
  min_score: 0.25               # 이하이면 "근거 부족"으로 처리
  rerank: false                 # MVP는 off, 정확도 필요 시 켠다
  hybrid: false                 # 키워드+벡터, 필요 시 켠다

constraints:                    # 검색이 아니라 강제 규칙
  dietary: hard_filter          # 식이제약은 필터로(AC1)
  cite_evidence: true           # 추천에 리뷰 근거 최소 1개(AC2)
  no_review_as_instruction: true # 리뷰 속 지시문 무시(AC4, 레드티밍 실습)

observability:
  log_tool_calls: true
  log_retrieved_chunks: true
```

### 작성 기준 및 설명

- **가장 중요한 줄은 `constraints:`다.** "식이제약은 검색이 아니라 필터"라는 한 줄이 이 제품의 성패를 가른다. 벡터 검색은 유사도지 보장이 아니다 — **지켜야 하는 것은 검색에 맡기지 않고 코드로 강제한다.** 강의 5에서 하드 필터로 정한 것이 여기서 설정으로 나타난다.
- **키마다 값의 근거를 주석으로 적었다.** `per_review`인 이유는 "리뷰가 짧아서"다. 청킹 전략은 문서의 성격에서 나오는 것이지 관례가 아니다.
- **`min_score`가 있다.** 검색은 언제나 무언가를 돌려준다 — 관련 없는 것이라도. 임계값이 없으면 "근거 부족"을 감지할 수 없고 결국 억지 근거로 추천하게 된다.
- **`rerank`, `hybrid`를 false로 두고 남겼다.** MVP에서 끄되 설정 항목은 만들어 둔다. LLMOps 강의 때 이 값을 바꿔 가며 실험한다.
- **설정을 코드가 아니라 YAML로 뺐다.** 파라미터를 바꿔 가며 측정하는 것이 강의 7과 LLMOps 강의의 작업이다. 코드에 박아 두면 실험을 못 한다.
- **`observability`가 설정에 들어 있다.** 무엇을 검색해 왔는지 로그가 없으면 왜 그 추천이 나왔는지 사후에 알 수 없다.

**새로 작성할 부분** — 대상 문서, 청킹 전략, 파라미터 값, 제약 목록.

**재사용 가능한 부분** — YAML 절 구성(source/chunking/embedding/store/retrieval/constraints/observability), 값마다 근거 주석, `min_score`로 근거 부족 처리, 지켜야 할 제약을 `constraints:`로 분리, 설정을 코드에서 빼기.

## D. 오케스트레이션, 실패 처리, 가드레일

### 단골 예시 — 5~8절

**5. 오케스트레이션 — workflow로 충분**

- 왜 workflow인가: 작업이 선형(파싱→검색→랭킹→정리)이라 단계를 사전에 열거할 수 있다. 모델이 다음 단계를 정할 지점이 없어 에이전트 루프가 필요 없고, 멀티 에이전트는 조율 비용만 늘린다.
- 멈춤 조건: 추천 1건 생성, 또는 후보 없음. 최대 도구 호출 횟수 상한을 둔다.

**6. 실패 처리 (실패를 전제)**

- 후보 없음 → 조건 완화를 제안(추천을 지어내지 않는다)
- 검색 근거 부족(min_score 미달) → 근거 부족을 밝히고 낮은 신뢰로 표시
- 예약 실패(mock) → 재시도/대체 슬롯 제안
- 호출 이상 → 최대 호출 상한과 타임아웃으로 차단

**7. 가드레일과 보안 (검증 및 테스트 강의, AI 보안 강의와 연결)**

- 식당명 환각 금지: 존재하는 데이터만 사용
- 식이제약 절대: 하드필터로 강제
- 리뷰는 데이터지 명령이 아님: 리뷰 텍스트 내 지시문 격리(프롬프트 인젝션 방어, AI 보안 강의)
- 모든 판단은 근거를 인용

**8. 관측(observability)**
모든 도구 호출(입력, 출력, 소요 시간)을 구조화 로그로 남긴다. evals(강의 7)와 운영(LLMOps 강의)의 입력이 된다.

### 작성 기준 및 설명

- **"workflow로 충분하다"에 이유를 붙였다.** 단계를 사전에 열거할 수 있으면 모델이 다음 단계를 정할 필요가 없다. 에이전트 루프와 멀티 에이전트는 비용과 조율 부담만 늘린다. **안 쓰기로 한 결정에 이유를 적는 것이 이 절의 핵심이다.**
- **멈춤 조건과 호출 상한이 있다.** 호출에 상한이 없으면 비용과 시간이 통제되지 않는다. 오케스트레이션에서 가장 먼저 정할 것이 "언제 멈추나"다.
- **실패 처리를 유형별로 나누었고 모두 "지어내지 않는다"로 수렴한다.** 후보가 없으면 없다고 말하고 조건 완화를 제안한다. LLM 제품에서 가장 빈번한 사고는 실패를 실패로 드러내지 않는 것이다.
- **가드레일이 AGENTS.md의 절대 규칙과 같은 문장이다.** 규칙 → 아키텍처 → 테스트가 같은 문장으로 이어진다. 새 규칙이 여기서 처음 등장한다면 AGENTS.md에도 넣어야 한다.
- **관측이 별도 절이다.** 로그는 나중에 붙이는 것이 아니라 아키텍처의 일부다. 강의 7 evals와 LLMOps 강의의 측정이 전부 이 로그에서 나온다.
- **비범위 절(9절)이 있다.** 결제, 실제 예약 API, 배달, 멀티에이전트, 파인튜닝. 스펙의 비포함, 온톨로지의 범위 밖과 같은 경계가 세 번째로 반복된다.

**새로 작성할 부분** — 오케스트레이션 방식, 실패 목록, 가드레일 전부.

**재사용 가능한 부분** — 오케스트레이션 방식 선택에 이유 붙이기, 멈춤 조건과 호출 상한 명시, 실패를 유형별로 나누고 각각의 대응을 적기, 가드레일을 AGENTS.md와 같은 문장으로 유지, 관측과 비범위를 독립 절로 두기.
