## A. 인터뷰 프로토콜

- **대상(누구를, 왜)**: 최근 수학 연계문항을 직접 제작하거나 검토한 수학 문항 제작자와 학원 수학 강사. 자신이 다룬 문항 하나의 제작·검토·처리 과정을 설명할 수 있는 사람을 대상으로 한다.
- **수집 방법**: 구글폼 서면 응답. 서로 다른 응답자 10명(B절 R1~R10)이 각자 최근에 다룬 연계문항 하나에 대해 서면으로 답했다. 원 응답은 팀 구글폼에 보관한다.
- **알아내려는 것(가설)**: 연계문항을 만들 때 핵심 풀이 의도를 유지하면서 조건 누락과 의도하지 않은 풀이를 막는 검토·수정에 반복 작업이 든다.
- **질문 5개 — 과거의 문항 하나를 따라가는 형태로**
  1. 최근 직접 만들거나 검토한 연계문항 하나를 처음부터 얘기해 주세요. — 구체적인 사건과 본인의 역할 확인
  2. 당시 어떤 원본문항과 자료를 참고했고, 어떤 풀이를 남기려 했나요? — 실제 사용 자료와 제작 의도 확인
  3. 초안을 만든 뒤 어떻게 풀어 보거나 검토했나요? 그때 무엇을 발견했나요? — 검토 행동과 발생한 문제 확인
  4. 발견한 뒤 무엇을 바꾸거나 그대로 두었나요? 확인과 수정에는 각각 얼마나 걸렸나요? — 우회로와 실제 비용 확인
  5. 최종적으로 그 문항을 채택·보류·폐기한 이유는 무엇이었나요? — 최종 행동과 판단 기준 확인
- **피해야 할 유도 질문**: ❌ “AI가 검토해 주면 쓰시겠어요?” → ✅ “지난번에는 문항을 어떤 방법으로 검토하셨어요?”
- **원칙**: 미래의 사용 의향을 묻거나 우리 팀의 해결책을 먼저 설명하지 않는다.

**도출된 페인 (누적)**

1. **조건 수정 반복** [문제] — 오류를 고친 뒤 다른 조건과 풀이 경로를 다시 확인해야 함 (로그 1, 3, 4, 6, 7, 8)
2. **의도하지 않은 풀이와 불충분한 조건** [실패 유형] — 목표한 답이나 풀이가 정해지지 않아 조건을 다시 설계함 (로그 2, 3, 4, 7)
3. **정의역·경계값·존재 조건 누락** [실패 유형] — 적용 가능 여부와 경계 사례를 따로 풀어 봐야 함 (로그 3, 7, 8, 10)
4. **풀이 의도와 수업 범위의 조율** [제약] — 수정할 때 제작자의 풀이 의도를 유지하려는 요구(로그 1)와 수업 범위에 맞춰 풀이를 조정해야 하는 요구(로그 9)가 있음
5. **난도 불일치의 처리와 학생 검증 부재** [제약] — 난도가 맞지 않으면 용도에 따라 사용하거나 보관하고(로그 2), 실제 학생 풀이로 난도가 확인되지 않은 경우가 있음(로그 5)
6. **직접 풀이와 AI 검토의 병행** [우회로] — 직접 풀거나 다른 사람·AI에게 다시 풀게 해 검토함 (로그 2, 3, 4)

## D. 핵심 Job Story

> 연계문항 후보를 검토할 때, 나는 원문의 풀이 의도를 살리면서 조건 누락과 의도하지 않은 풀이를 확인하고 싶다. 그래서 문항을 채택할 수 있는지 판단하고 필요한 부분만 수정할 수 있도록. (로그 1, 2, 3, 4, 6, 7, 8, 9, 10)

| 요소 | 내용 | 근거 |
| :--- | :--- | :--- |
| 상황(트리거) | 만든 연계문항 후보를 검토하고 처리할 때 | 로그 1, 2, 3, 5 |
| 기능적 Job | 풀이 의도를 유지하며 조건과 수학적 성립을 확인하고 수정·채택 여부를 결정 | 로그 1, 2, 3, 4, 7, 8, 9, 10 |
| 감정적 Job | 오류를 놓치지 않았다는 확신이 필요한지는 확인되지 않음 | 미확인 |
| 사회적 Job | 다른 사람에게 좋은 제작자로 보이고 싶은지는 확인되지 않음 | 미확인 |
| 현재 고용된 대안 | 직접 다시 풀기, 동료나 AI의 독립 풀이, 조건 수동 수정 | 로그 2, 3, 4, 7, 8 |

## E. 미니 온톨로지

- **반복된 명사 → 클래스·속성 후보**: 수학 문항 제작자·학원 수학 강사 → `QuestionDeveloper`, 제작 목표 → `GenerationRequest`, 원문항·연계 후보 → `Question`, 조건·경계값 → `Condition`, 핵심 풀이 → `SolutionIdea`, 난도 → `DifficultyProfile`, 검토·판정 → `ReviewResult`
- **반복된 동사 → 대표 관계 후보**: 원문을 사용하다 → `uses_source`, 핵심 풀이를 유지하다 → `preserves`, 문항을 만들다 → `produces`, 조건을 포함하다 → `contains`, 검토 결과를 받다 → `receives`
- **동의어 통합**: 원문항 = 기출 = 원본 → `Question(SOURCE)`; 변형문항 = 연계문항 = 후보 → `Question(CANDIDATE)`; 핵심 풀이 = 풀이 발상 → `SolutionIdea`
- **범위 밖**: 결제·판매·정산, PDF 수식 복원, 공간도형 자동 작도, 학생 데이터 없는 정답률 확정

클래스·속성·관계와 각각의 `evidence:`를 적은 미니 온톨로지 YAML은 [ontology.yaml](../ontology.yaml)에 있다.

**핵심 흐름 (전체 7개 클래스)**

```text
QuestionDeveloper --(defines)--> GenerationRequest
GenerationRequest --(uses_source)--> Question(SOURCE)
GenerationRequest --(preserves)--> SolutionIdea
GenerationRequest --(targets)--> DifficultyProfile
GenerationRequest --(produces)--> Question(CANDIDATE)
Question(CANDIDATE) --(derived_from)--> Question(SOURCE)
Question(CANDIDATE) --(contains)--> Condition
Question(CANDIDATE) --(receives)--> ReviewResult
```

`Question(SOURCE)`와 `Question(CANDIDATE)`는 하나의 `Question` 클래스에서 `question_role` 값으로 구분한다.
